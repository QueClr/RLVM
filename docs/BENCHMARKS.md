## What the numbers are

- **Order (owner note 12): warm wall clock with 8 workers and pipelined loading, warm wall clock with 1 worker, cold
  wall clock of a fresh process, CPU time, peak RSS, instructions.** The first two are in the section "Warm wall
  clock" at the end (`bench/warm.sh`: the same process checks the same export again; full table in
  `work/status/warm.md`). Every OTHER table here is one fresh process per run on a batch load (what the arena
  runs), i.e. cold wall clock and its CPU time, which charge the warm-up that the owner's target does not.
  CPU time is `perf stat` task-clock summed over all threads and child processes; instructions are user-space
  instructions; peak RSS is GNU time's maximum resident set size of the process tree's largest process.
- **Where**: this host (aarch64; Cortex-X925 performance cores), one fresh container per run, shaped like the arena
  runner: 8 CPUs, 16 GB, no network (`bench/arena-docker.sh --arena-limits --no-network bench/measure.sh`). The arena
  itself runs on x86-64; absolute numbers differ, ratios between checkers carry over only roughly.
- **RLVM columns**: one per engine (`-X engine=NAME`), native image, `--threads 8`, batch load, the arena's
  run line otherwise (`scripts/arena/rlvm.yaml`, whose own thread count is 4). **RLVM machine** is the engine that will
  ship (`rlvm-machine`: the worklist machine; today it runs only when named, and a unit it declines is checked by the
  reference engine, whose time is then part of the figure); **RLVM reference** is the fallback and re-check engine,
  today's default. native = the CE native image `bin/rlvm` (`-O3`); JVM = `bin/rlvm-jvm` (GraalVM CE 25, SerialGC,
  13 GB heap, so its RSS is mostly heap reservation that was touched). Which launcher ships and why: `docs/PLATFORM.md`.
- **Rows**: every corpus of the ladder with a machine result; the others are listed at the end with the reference engine.
- **Which machine, and when**: the jar `608b84b2b142` (the wave-4 integrator's final jar) in the distribution `work/steward/w7/dist` (CE native image `-O3`), default switches (v0). Its figures are the eight-worker runs of the platform matrix (`docs/PLATFORM.md`, section I.2: two runs per corpus and launcher, 13:33Z to 13:49Z, host load 26 to 95), entered into the history by `work/steward/w7/import-matrix.py` - the same measurement as `track.py` makes (`bench/measure.sh` around the run line in a fresh arena-shaped container). The `track.py` entries of 14:20Z (three runs each; they included the full cedar corpus: 20.65 s CPU, 0.61 times the reference engine's) were taken while the host was thrashing and are marked invalid (orchestrator, `work/status/requests.log` 14:32Z). The machine decided every unit of these corpora itself; the reference engine re-checked none (`docs/PLATFORM.md`, section I.6).
- **Baselines**: gruszka, nano-lean and the official checker (`leanchecker`, arena version v4.35.0) with the run lines
  of the arena's checker definitions (gruszka and nano-lean use 4 threads, the official checker one), measured the
  same way on the same host (`docs/research/12-baselines.md`, `bench/baselines.json`).
- **Figure of a cell**: minimum CPU time and wall clock over the runs of the entry (other containers share the eight
  cores and can only add time), maximum RSS, median instructions. The run count, the date and the host's load
  average are in the provenance table at the end. `-` = not measured on this host.
