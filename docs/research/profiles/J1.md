# J1: the JVM as the warm platform (HotSpot of GraalVM CE 25, machine engine)

Agent J1, 2026-11-24. Owner note 12 makes warm wall clock the metric: 8 parallel workers, steady state after JIT
warm-up, loading pipelined with checking; warm-up is reported, not charged. The first warm table
(`work/status/warm.md`) found the JVM launcher faster than the CE native image once warm and slower cold. This
report asks four things of the JVM launcher with the machine engine: is its steady state as good as HotSpot can
do (section 2), how fast does it get there and can it start warm (section 3), how much memory does it need
(section 4), and what should the launcher ship (section 5). No module code was changed; findings for the
machine's owners are in section 6.

**What C2 does hit is its inlining budget.** The entry steps call their sub-judgments directly, the continuation
steps are small, and C2 inlines depth-first in bytecode order. In the big loops it expands the first hot chain
until the compile unit is full: `NodeCountInliningCutoff` (18,000 nodes at parse time) and `DesiredMethodLimit`
(8,000 inlined bytecodes) are **develop flags, constants in a product VM**; `MaxInlineLevel` (15) is the third
wall. After that, hot callees later in the same method are left as calls:

| compile unit (root), last C2 compile | inlined bytecodes | code bytes | depth | hot call sites refused for the budget (profile count at the site) |
|---|--:|--:|--:|---|
| `Infer.piLoop` | 10,611 | 55,088 | 17 | inlining too deep 524 M (292 M of them `Terms.kind -> Terms.arr`); size > DesiredMethodLimit 21 M; NodeCountInliningCutoff 3 M |
| `Conv.bindLoop` | 10,368 | 49,408 | 15 | NodeCountInliningCutoff 56 M (`Eval.flat -> Terms.kind / regionOf / Node.wordOf`, `Eval.eval -> Eval.enter`) |
| `MachineSession.run` | 10,144 | 37,904 | 17 | inlining too deep 55 M (`Terms.a -> Terms.arr` 42 M) |
| `Infer.twY` | 8,852 | 43,944 | 17 | inlining too deep 23 M; size > DesiredMethodLimit 4 M (`twY -> twE`) |
| `Conv.convLoop` | 10,649 | 52,784 | 15 | NodeCountInliningCutoff 5.9 M: the second `convPass` and `convCore1` (the core of conversion) stay calls because `convBind -> cbind -> bindLoop -> bindDom -> Eval.dom ...` was parsed first |

(`work/j1/tools/budget.py`; 944 C2 units of `rlvm.*`, 2.56 MB of code in total; these five are the ones still
over the budget in their last compile; earlier compiles of `Infer.twalk`, `Reduce.coreLoop`, `Eval.args`,
`Eval.app`, `Cargs.cargsFrom`, `Conv.lazydLoop`, `Conv.lstepBoth` reached 18,300-18,900 nodes too.)

Three more patterns from the inlining log (all C2 compiles, counts are the profile counts C2 saw):

- **"too big" at cold-looking arms of a shared dispatcher.** `Eval.atom` (312 bytecodes, a switch) is inlined
  into `Eval.eval`, but its arms `Values.mkConst` (71 b, 16 M of atom's 50 M calls at that site),
  `Levels.lsubList` (127 b), `Eval.closedGet` (120 b), `Levels.lsub`, `Values.mkSort` (39 b) are refused as "too
  big": a callee above `MaxInlineSize` (35) is only inlined when its site runs in at least 25 % of the caller's
  invocations (`InlineFrequencyRatio`), and that frequency is scaled by the share of the caller's profile that
  belongs to the inlined copy. A dispatcher that is called from several places never has a "hot" arm.
- **"already compiled into a big method"** (386 M): `Values.closureAt` (318 b), `Eval.app`, `Infer.twArg`,
  `Conv.k_cbind5`: C2 calls the existing nmethod (above `InlineSmallCode` = 2,500 bytes of code) instead of
  inlining. That is the mechanism working as intended.
- **"recursive inlining is too deep"** (149 M): `Infer.inferApp -> Infer.infer`, `-> Infer.twalk`,
  `Reduce.coreHead -> Reduce.core`: the recursive entry steps; one level is inlined (`MaxRecursiveInlineLevel` 1).

The profile itself is flat (JFR, last two passes, 3,823 samples): the hottest self frames are table probes -
`Runs.sameKept` 8.3 %, `Values.closureAt` 6.3 %, `Values.neu` 4.8 %, `Eval.atom` 4.8 %, `Values.closureProbe`
3.7 %, `Eval.app` 3.7 %, `Eval.gate` 3.6 % - and no compiled method holds more than 8.2 % (`Values.closureOverNew`,
`Eval.args` 7.9 %, `Eval.applyFrom` 7.4 %). `Machine.growVtab` + `growRtab` are 2.6 % of a warm reload pass (the
sessions of a new pass grow their tables again).

**Answer to question 1.** HotSpot's steady state on the machine is not limited by anything a flag can lift:
every hot method is compiled by C2, nothing bails out, and making C2 inline more, less or differently does not
move the warm pass beyond the noise. Two flags have a consistent sign and are free: transparent huge pages
(-2 to -4 %, TLB reach for a store of gigabytes) and, with one worker, C2 without the C1 tiers (0 to -7 %).
That fits the profile: the hot frames are probes into large tables, i.e. memory, not instructions.

## 3. Warm-up, and starting warm

### 3.1 What GraalVM CE 25's JDK supports (verified, not assumed)

`java -XX:+UnlockDiagnosticVMOptions -XX:+PrintFlagsFinal -version | grep -i aot`: `AOTCache`, `AOTCacheOutput`,
`AOTConfiguration`, `AOTMode`, `AOTClassLinking` (product: JEP 483 and the one-command form of JEP 514),
`AOTRecordTraining` / `AOTReplayTraining` (diagnostic, switched on by the VM when a cache is written / used: the
method profiles of JEP 515). There is no AOT code in JDK 25 (the cache's code region is 0 bytes): the cache
makes classes load linked and tells the JIT what to compile, it does not carry machine code.

| test (`work/j1/aot/*.log`) | result |

So on this JDK the AOT cache and JVMCI exclude each other: with the cache the VM cannot run Graal as its JIT and
the Truffle tier (`rlvm-truffle`, switch `t2`) has no compiler. For the machine's default switches (no Truffle
tier; C2 as the JIT) nothing is lost.

What the cache changes in the first second (`-XX:+PrintCompilation` on init-prelude, `work/j1/diag/printcomp-*`):
without it the VM compiles at tier 3 first (full profiling, the slowest compiled code) and C2 follows when the
profiles are ripe; with it the methods that the training run saw at tier 4 are compiled at tier 2 (no profiling)
at once and queued for C2 with the training profile. The C2 compiles themselves still have to be done.

Reading:

- **Compiler threads are the lever.** With `CICompilerCount=2` a tiered VM has one C2 thread, and it shares
  eight cores with eight workers that are still running interpreted and C1 code: Init needs four passes (4.3, 1.8,
  1.2, 1.0 s). With 8 compiler threads the cold wall falls from 5.3 to 2.9 s on Init and from about 8.5 to 5.8 s
  on cedar, pass 2 is within 20 % of steady and pass 3 is steady. The steady state does not suffer (0.85 against
  1.00 s on Init in the same window). A first pass with 6 workers instead of 8 does the same thing from the other
  side (3.45 against 4.74 s cold): the two free cores go to the compilers.
- **Without the C1 tiers** both threads of `CICompilerCount=2` are C2 threads and the first pass is shorter still
  on a real corpus (Init 2.79 s cold, cedar pass 1 4.4 s) although everything starts in the interpreter. On a tiny
  input it is the other way round (section 3.3).
- **Class loading is not the cost.** A classic CDS archive (4.69 s) and the AOT cache with its profiles switched
  off (4.10 s) are where JVMCI-off alone is (3.97 s): loading and linking 1,300 classes is 0.1-0.2 s of a 4 s
  start.
- **The profiles of the cache do shorten the start**: with 2 compiler threads 2.90 s against 4.74 s (3.97 s for
  its control); with 8 threads the gain shrinks to 0.5 s on Init (2.33 against 2.87) and 1.1 s on cedar (4.69
  against 5.75).
- **... and they make the steady state worse.** In every pair the later passes of the run with the cache are
  slower: Init 1.01 against 0.85 s (8 threads), 0.95 against 0.84 (untiered); cedar 2.18 against 2.01 and 2.05
  against 1.99. Confirmation with 10 passes in section 3.3.
- **The cache trained on init-prelude** (3.8 MB, what a build always has) gives less than the one trained on Std:
  cold 5.78 s on cedar, i.e. nothing, and 3.41 s on Init with 4 threads against 2.35 s.

the same direction). The VM compiles from the training run's profiles at once and has no reason to compile
again: the code is correct, a little worse, and stays.

Where the difference is (`-XX:+LogCompilation` on Init, 8 workers, 6 passes, with and without the cache;
`work/j1/diag/init-8w-comp-*.summary.txt`; a diagnostic on the loaded host):

| | without the cache | with the cache |
|---|--:|--:|
| compile tasks at tier 3 (C1, full profiling) / tier 2 (C1, no profiling) | 2,017 / 860 | 184 / 1,945 |
| C2 compile units of `rlvm.*` (last compile of each root) | 932 | 1,012 |
| ... of them at the inlining budget (8,000 or more inlined bytecodes) | 12 (0.46 MB of code) | 25 (0.92 MB) |
| C2 code of `rlvm.*` | 2.65 MB | 3.43 MB |
| uncommon traps taken at run time | 246 | 25 |

The run's own profile is young when C2 first compiles a method: branches not seen yet are compiled as traps, a
few hundred of them fire, and the recompiled code contains what this run needs. The trained profile has seen
four passes of Std: nearly every branch has a count, C2 compiles all of them (25 traps in the whole run), the
units are a third larger and twice as many of them run into the inlining budget of section 2.1. A mature profile
is the worse one for this code.

A tiny input (init-prelude, 3.8 MB, 1,840 units), cold wall of a fresh process, three runs each: today's flags
0.21 / 0.22 / 0.22 s; candidate flags 0.25 / 0.25 / 0.24; with the cache 0.22 / 0.23 / 0.25; untiered 0.33 /
0.40 / 0.37; native image 0.02 / 0.02 / 0.02. The JVM's floor is about 0.2 s whatever is done; `-TieredCompilation`
costs 0.15 s there.

**Answer to question 2.** (a) The JVM reaches its steady state in two passes instead of four when it has compiler
threads: `-XX:CICompilerCount=8` (cold wall 5.3 -> 2.9 s on Init, about 8.5 -> 5.8 s on cedar, nothing lost in
steady state); `-XX:-TieredCompilation` gets the same first pass with two threads. Lower tier thresholds were not
measured (section 7): the queue of the one C2 thread, not the thresholds, is what holds the first pass back.
(b) It can start warmER,
not warm: JDK 25's AOT cache works on GraalVM CE 25 only with JVMCI off, takes another 0.4-1.1 s off the cold
wall (Init 2.3 s against the image's 1.1 s), costs 18.7 MB and 12-50 s of build time, and **costs 5-9 % of the
warm wall clock**, which is the metric. It does not belong in the default launcher line; it is an option for a
launcher that is known to run once.

### 3.4 What it would take to ship the cache (if it is wanted for cold runs)

Prototype: `work/j1/tools/mkproto.sh` builds a distribution with the proposed launcher
(`work/j1/proto-src/rlvm-jvm.in`) and writes `lib/rlvm.aot` with one training run through that launcher;
`work/j1/proto-aot` is the result (cache trained on Std, 4 passes).

1. **Build step** (in `scripts/build.sh`, after the jars and the launcher are in the staged distribution, before
   it is installed): one run of the staged launcher on a training export with
   `RLVM_EXIT=exit` and the VM flags `-XX:-EnableJVMCI -XX:AOTCacheOutput=<stage>/lib/rlvm.aot`, e.g.
   `-X engine=machine -X load=pipelined -X passes=4 --threads 8 Std.ndjson`. JEP 514's one-step form does the
   rest (the VM starts a child VM at exit that assembles the cache). Cost: the training run (Std x 4 passes: about
   12 s on quiet cores, 95 s on this host under load) plus 2-3 s of assembly. Size: **18-19 MB** next to 20 MB of
   jars. Nothing is downloaded; it is the build's own JDK.
2. **Training export.** init-prelude (always there) is not enough (section 3.2); Init or Std is. The arena build
   has `init.ndjson` only if the site generated it; the PGO path of `build.sh` already has a `--train FILE` option
   that could be shared.
3. **Launcher.** (a) add `-XX:-EnableJVMCI -XX:AOTCache=$here/../lib/rlvm.aot` when the file exists and nothing
   needs JVMCI (the Truffle tier `t2`, `--truffle-probe`, a user's `-XX:+UseJVMCICompiler`); (b) spell the class
   path out in sorted order instead of `lib/*`: the cache is accepted only for the class path it was trained
   with, and the VM expands the wildcard in directory order, which is not the same on every file system; (c)
   `-Xlog:disable -Xlog:all=warning:stderr`, because a refused cache prints three `[error][aot]` lines on standard
   output and the run goes on; (d) `RLVM_EXTRA_CP` entries are appended after the trained class path, which the
   cache allows.
4. **What invalidates it** (the run then goes on without it): any jar with another size or modification time
   (so the cache is written after the last jar is in place, and distributions are copied with `cp -a`, as
   `cp -aL work/dist DIR` already does; a `cp -r` copy was refused); another JDK build; `UseCompactObjectHeaders`
   different from the training run; JVMCI on. Heap size, collector (Serial and Parallel tried), compiler thread
   count, tiers on or off, huge pages and the code cache size may differ.
5. **What is lost.** Graal as the JIT and the Truffle tier's compiler in the same process (the launcher has to
   choose per run, as the prototype does).

## 4. Memory: the heap the machine needs on Mathlib

### 4.1 What decides it

- The launcher's `-Xms13g -Xmx13g -Xmn1g` exists for the reference engine (13.4 GB resident on Mathlib,
  `work/status/warm.md`). With the machine the live data after a full collection are **3.3-3.7 GB at the end of
  the load and 2.7 GB after it** (`-Xlog:gc*`, `work/j1/diag/mathlib-*.gc.log`); the resident set is anonymous
  memory only (`/proc/PID/status` once a second: RssFile 22 MB; the export does not stay mapped).
- HotSpot's serial collector collects the old generation only when it is full, so the resident set of a process
  with a large cap is whatever garbage the young generation promoted (the loader's publications, about 0.25 GB
  per young collection during the load) on top of the store. Nothing in the VM bounds it but `-Xmx`.
- **The machine has a heap rule of its own**, `Machine.heapAllows` (rlvm-machine `Machine.java`): before a session
  array of 32 MB or more grows, the new array must fit into `maxMemory - used` together with 256 MB, a second
  copy of itself (multi-worker engines) and a "young reserve" of **a third of the maximum heap**
  (`YOUNG_RESERVE = Runtime.maxMemory() / 3`: HotSpot's default `NewRatio`, although both launchers give
  `-Xmn1g`). If it does not fit, the machine calls `System.gc()` and looks again; if it still does not fit, the
  growth is refused, the unit is declined with `E_MEM` and the driver re-checks it on the cold path. These are
  the only full collections of a Mathlib run with the machine, and they are what a smaller cap changes.

### 4.3 Answer to question 3

- **Same warm wall clock from 13 GB down to 6 GB**: 23.94 / 24.07 / 24.21 / 23.99 s for 13 / 8 / 7 / 6 GB (CPU of
  the warm pass 179-182 s in all four).
- **Peak RSS**: 8.7 GB (13 GB, two passes; `warm.md` saw 11.5 GB after three) / 6.7 GB (8 GB) / 5.7 GB after one
  pass and 6.7 GB after two (7 GB) / **5.8 GB in every pass (6 GB)**. With the serial collector the resident set of
  a later pass is the cap: the pooled sessions no longer grow, so nothing asks for a collection before the old
  generation is full.
- **7 GB is the smallest cap at which the machine decides every unit it decides at 13 GB** (0 `E_MEM`); at 6 GB
  its own heap rule refuses 2-6 session growths per pass by a few tens of MB and calls `System.gc()` 28 times in
  two passes; at 5 GB (diagnostic) 18 refusals and 95 full collections.
- **What the launcher should choose** (it sees `-X engine=machine` in its arguments): machine `-Xmx7g -Xmn1g`
  without `-Xms` (5.7 GB resident for one check of Mathlib, under the 6 GB target; 6.7 GB only when the same
  process checks it again); every other engine today's `-Xms13g -Xmx13g -Xmn1g`. Once the machine's reserve
  follows the real young generation (finding J1-F1), `-Xmx6g -Xmn1g` is the line: 5.8 GB in every pass at the
  same wall clock, measured above with the 2-6 refusals it would no longer have.
- Not measured: a smaller young generation (`-Xmn512m` would take another 0.5 GB off the resident set and double
  the 27 young collections of a pass), and the reference engine with any other heap.

### 5.1 The launcher line


## 6. Findings for the machine's owners (no module was edited)

**J1-F1 (M6, `Machine.heapAllows` / `YOUNG_RESERVE`): the young reserve is a third of the heap whatever `-Xmn`
says, and that is what sets the machine's memory floor.** `YOUNG_RESERVE = Runtime.maxMemory() / 3`; both
launchers run with `-Xmn1g`. On Mathlib with `-Xmx6g -Xmn1g` the machine refuses 2 session growths in the first
pass and 6 in the second: `a session array of 33554432 bytes does not fit (2375316784 bytes free of 6335102976,
reserve 268435456)`, i.e. 2 x 32 MB + 256 MB + 2,112 MB = 2,432 MB wanted against 2,375 MB free, where the real
young generation is 1,024 MB; before each refusal it calls `System.gc()` (28 full collections in two passes;
with 13 GB: none). Reading the reserve from the VM (`MemoryPoolMXBean` of the young pools, or the
`NewSize` / `MaxNewSize` flags through `HotSpotDiagnosticMXBean`) instead of assuming `NewRatio` would make 6 GB
a clean cap: 5.8 GB resident in every pass at the wall clock of 13 GB (section 4). Evidence:
`work/j1/logs/w08-mathlib-base-x6g.{out,declines.txt,gc.log,stats.json}`.

**J1-F2 (machine owners; the convention H10): C2 compiles all of it, and its inlining budget is the only thing
it runs into; neither a flag nor a reshaping for the JIT is worth doing.** Evidence in section 2.1 (which
methods, which messages). `Infer.piLoop`, `Conv.bindLoop`, `Conv.convLoop`, `MachineSession.run`, `Infer.twY`
(cedar), `Infer.twalk`, `Infer.k_ck1/4/5`, `Cargs.cargsFrom` (Init) end at 8,900-11,200 inlined bytecodes and
18,000-18,900 nodes; C2 answers "NodeCountInliningCutoff", "size > DesiredMethodLimit", "inlining too deep" for
call sites with 10^6-10^8 profile counts, among them `Conv.convLoop -> convCore1` and `Terms.kind ->
Terms.arr` (292 M in `Infer.piLoop`). The flags that move those limits (`MaxInlineLevel` 9 / 25,
`MaxInlineSize=100`, `FreqInlineSize=600`, `InlineSmallCode` 1,000 / 6,000, `-ClipInlining`) change the warm
pass by nothing that repeats (section 2.2). So the source-level equivalents - folding the private three-way
select `Terms.arr` into `kind` / `a` / `b` / `fvMask` / `word` (one inline level less at the hottest leaf),
splitting the arms of `Eval.atom`, shielding entry steps with `dontinline` - should not be expected to pay
either; `h10/hotspot-inline.cmd` measured nothing on C2 before (NOTES-M6 F23) and this agrees. What does show up
in the profile is memory: the hottest frames are probes into session tables (`Runs.sameKept` 8.3 %,
`Values.closureAt` 6.3 %, `Values.neu` 4.8 %, `Values.closureProbe` 3.7 %), and huge pages are the one flag
with a consistent gain. A change that makes those probes fewer or denser will help more than any flag.

**J1-F3 (machine owners, M8): a mature profile gives C2 worse code for the machine than a young one.** With
the AOT cache the VM compiles from the profile of four training passes: 25 uncommon traps in a whole Init run
instead of 246, 3.43 MB of C2 code instead of 2.65 MB, 25 compile units at the inlining budget instead of 12, and
every later pass 5-9 % slower (section 3.3). The step methods have many rarely-taken arms (`*Slow`, `sig*`,
`spill*`, `fault`, the cold switch arms); C2's own pruning of branches it has not seen is doing useful work, and
whatever keeps rare arms out of the compile units (they are already out of line; the test in front of them is
what the profile sees) keeps the units inside the budget.

**J1-F4 (rlvm-driver / rlvm-main, P7 and the integrator): in a reload pass after the first, nothing asks for a
collection, so the resident set is the heap cap.** The only full collections of a machine run are the
`System.gc()` calls of `Machine.heapAllows`, which are made when a pooled session array grows; in later passes
they do not grow. Mathlib, `-Xmx7g`: 5.7 GB after pass 1, 6.7 GB after pass 2 (13 GB: 7.9 / 8.7 GB; `warm.md`
11.5 GB after three passes). It is a property of the benchmark mode, not of a single check; the driver's
`gc-after-mib` exists for it.

**J1-F5 (rlvm-export, LP2; small): the reader's block loop stays in C1 code.** `ExportReader.sequential` runs
once per load with about 20,000 iterations on cedar, so it never reaches the tier-4 back-edge threshold: after
five passes it still runs as tier-3 OSR code (with full profiling). Its body is calls into C2 code, so the cost
is small; `Worker.run` (the worker's unit loop, 1,092 bytecodes) reached tier 4 only in pass 5 for the same
reason. Nothing to do unless a profile of the loader shows the shell.

## 7. What was not established

- **Effects below about 5 %.** The host was shared for the whole session (load average 20-60); two base rows of
  one window differ by up to 5 % with 8 workers. Every "nothing" above means "nothing above that".
- **Why exactly the cached profile costs 5-9 %**: the larger compile units are an observation on one diagnostic
  pair (Init), not a proof of cause.
- **Tier thresholds** (`Tier4InvocationThreshold` etc.) and `LoopUnrollLimit`, `MaxNodeLimit`,
  `-DontCompileHugeMethods` were not timed (the last three have nothing to act on, section 2.1). Given J1-F3,
  LOWER tier-4 thresholds (younger profiles) are the one JIT experiment left that could move the steady state.
- **One worker on Mathlib** (about 190 s per pass) and **Graal on Mathlib** were not run.
- **The reference engine** was not measured with the proposed flags; its heap line is unchanged.
- **Huge pages elsewhere**: this host has transparent huge pages in `madvise` mode, where the flag takes effect.
  With `never` the VM prints one warning and runs as today; with `always` the flag changes nothing. A container's
  setting is the host's.
- **x86**: every number here is aarch64 (Cortex-X925). The arena's runner is x86; the JVM launcher is not what the
  arena runs.
- **A smaller young generation** on Mathlib (`-Xmn512m`) and the 6 GB cap after a fix of J1-F1.
- **A cache trained on Init** (between init-prelude, which is not enough, and Std, which is).
