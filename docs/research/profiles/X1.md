# X1 - few bits of reference count and in-place reuse in the hash-consed store

Scout report, 2026-11-24. Subject: the owner's idea to borrow from Reussir the few-bit reference count (in the limit
one bit, unique / shared) that licenses in-place reuse - "may not be a good idea; use whatever good specialization /
JIT trick you can think of". Method: a census of every record and run the machine makes (who made it, was it ever
found again, who holds it, is it dead when the judgment that made it returns), four candidate schemes judged against
it, prototypes of what the census points to, counters first, then time. Living summary: `work/status/prof-X1.md`;
working files: `work/prof/X1/`. Everything here is the JVM launcher with ONE worker, on the main tree of
`rlvm-machine` as it was at 15:09Z (the tree has moved since: section 5.3).

## 0. Verdict in one page

1. **The bit of Reussir has nothing to bite on in this store, and the census says why.** The cases it specialises -
   extend the spine just built, extend or prune the frame just built, bump a Nat offset cell - are 1.9-7.2 % of the
   records, 0.4-3.4 % of the new frames and a few hundred cells per corpus; working environments are already a LIFO
   slab (1 copy in 162 M pushes over the nine census runs); and where the case occurs the source is held by a memo
   word or an environment (by nothing in 0.0 % of the cases in v0). Rewriting a hash-consed record in place trades
   an insert for a delete: it saves bytes, not a probe. Schemes (a) fresh-top rewrite, (c) 2-bit header counts:
   **no-go**; (d) builders: **already the design**; (b) region rollback: **no-go as a speed-up**. None of these four
   was built; the verdicts rest on the census.
2. **What IS unshared is the memo key, not the value.** The largest class of records everywhere is the tabling record
   of EVAL - 25 % of all records on the Cedar slice, 35 % on Init, 43 % on reachability, still 22 / 30 / 39 % under
   `warm,gated,expect` - and 82-99.5 % of them are never found again; each also cost a PRUNE and often a frame. On
   reachability 97.5 % of ALL records are never found again.
3. **So the one bit goes on the KEY** (`once`, 117 lines in `Eval.java`): one bit of visit count per tabling key in a
   Bloom filter outside the store; the first evaluation of a key makes no frame and no record, the second is tabled
   as today, so a key is evaluated at most twice. Counters against v0: records -18 % (Cedar slice), -30 % (Init),
   -28 % (Std), -29 % (con-leche), -41 % (reachability: 22.9 M -> 13.5 M); ticks +5.8 % / +5.4 % / +5.7 % / +5.3 % /
   +0.7 %; peak RSS of the JVM on reachability 3,052 -> 1,533 MiB. **Warm check time (`bench/quiet.py`, last pass of
   a process): reachability -27 % against v0 (5,687 -> 4,143 ms; cold first pass -23 %) and -29 % against
   `warm,gated,expect` (5,585 -> 3,972 ms).** Init under `warm,gated,expect`: about -6 % (one process, below all
   three baseline processes). Cedar slice, and Init against v0: no resolved change (-1.3 %, -1.0 %; the samples
   overlap). The gain is where sessions are large; where they are small it is memory only.
4. **The second idea did not survive the clock.** `evc`, an ephemeral EVAL memo with the key inline in front of the
   filter, does in counters exactly what it was built for (alone: every counter identical to v0; with `once`: ticks
   +1.0 % / +0.6 % / +0.2 % instead of +5.8 % / +5.4 % / +0.7 %; under `warm,gated,expect` 2-11 % FEWER ticks than
   the base) - and in time it is never ahead of `once` alone: +7.9 % alone on the Cedar slice, 6.7 % and 10.4 %
   slower than `once` alone on reachability (v0, s1). Ticks are not time. **No-go as built**; so is the per-node
   two-bit counter `prof`.
5. **Correct on everything it was run on**: the machine's accepted / rejected / declined counts are equal with the
   switches off and on in all 28 counter runs of six corpora; per declaration against the reference engine (M8's
   harness): no SOUNDNESS and no COMPLETENESS line in any report - tutorial 395 / 395 units agree, bugs 1,427 of
   1,428, the Cedar slice 8,407 of 8,418, reachability 4,405 of 4,413, Init 58,383 of 58,547 (`evc + once`), and
   every decline is the base tree's own eager-reduction decline. `once` alone: tutorial and bugs on the measured
   tree, and tutorial, bugs, the Cedar slice and reachability on the patched main tree of 16:53Z (section 5.3).
6. **Hand-over**: `work/prof/X1/patches/0001-eval-visit-filter.main-1653Z.patch`, one file, owner M2. Not
   established: 8 workers, the native image, steady state beyond three passes, the large corpora (section 7).

## 1. What was measured, and how

**Trees.** `scripts/machine-sandbox.sh init X1` refuses ("work package 'X1' owns nothing in OWNERS.tsv"; `test` and
`pull` likewise), and claiming a file would edit the main tree. So: a copy of the main tree of `rlvm-machine` taken
under the sandbox lock at 15:09:21Z (after S's publication of 15:08:59Z; the last code publication in it is M6's of
15:07:19Z) at `work/sandbox/X1/rlvm-machine`, a pristine twin `work/prof/X1/base1507/rlvm-machine` for the diffs,
both built with the command that `test` runs (`$MVN -o -q -f .../pom.xml -Drlvm.root=$PWD`). Nothing was published.

**Census build** (`work/prof/X1/census/`): the base tree plus 54 exact-string hooks (`instrument.py`; every hook must
match exactly once, so a source that moved fails loudly) and one class `Shadow.java`. No value, memo word, tick or
table entry differs from the uninstrumented machine (the counters `records`, `runWords`, `ticks`, `pairs`, accepted
and declined of the statistics file are identical in both builds in the 14 census runs, of 15, that have an
uninstrumented twin). Shadow arrays indexed by record id and run id hold: who
made it (the EVAL site, or "other" = INFER / CONV / reduction), the event at which it was made, the number of later
intern probes that found it and the event of the last one, the event at which the EVAL judgment that made it
completed. One event = a new record, a new run, a probe hit or a completed EVAL node; ticks are sampled every 64
events for the lifetime histograms. At every session end (`Machine.reset`, `MachineSession.close`) the session is
scanned once:

- **found again**: at least one later intern probe returned the record (the benefit of hash-consing);
- **E0**: never found again and referenced by nothing at the end of the session (no slot, field or memo word);
- **TE** (transitively ephemeral): never found again, and every referrer is itself TE (a reference-count cascade from
  the E0 records): no later probe ever reached it or anything that holds it;
- **dead at the return of the judgment that made it**: the record was made between `Eval.node` and `Eval.done` of an
  EVAL node (innermost; a tabling record belongs to the evaluation it tables), it is not that judgment's result, and
  after the judgment completed it was neither found by a probe nor stored into a newer record or run, nor is it
  reachable (fields, slots, memo words) from a record that is live in this sense. Records made outside any EVAL node
  (by INFER, CONV, the reduction judgments) have no such return event; for them the tables give "never live again"
  (never found and not reachable from a live record). Reads through a Java local are invisible to the census, so
  "dead" is an upper bound on what a region could release, and "result" counts as live however short it lives;
- **copy logs**: every NEU made by extending another NEU, every NSUC made from an NSUC, every new frame with the
  frame whose ENTER started the environment it was pruned from; classified at the session end (was the source the
  newest record or run; was it ever touched again; is it TE).

**Runs.** JVM launcher, one worker, 6 GB heap, one host slot per batch; the machine as primary engine with no switch
(**v0**: every non-leaf node tabled, one session per declaration) and with `warm,gated,expect` (**s1**, the candidate
default of the integration log; session cap 4 MiB). Corpora: `init-prelude` (smoke), Init, Std, the Cedar slice
`cedar-hot-ax`, reachability, and con-leche as the additional project corpus. In all of them the machine as copied
declines the declarations that enter eager reduction (M6's `erDeclines` of 15:07Z; the statistics count 22 declines
on the Cedar slice = 11 units, 328 on Init = 164 units, 16 on reachability = 8 units, 406 on Std, 176 on con-leche);
the reference engine checks those. Raw data:
`work/prof/X1/census/data/*.tsv` (+ the statistics file of each run); per-run tables: `work/prof/X1/census/tables/`.

**Prototype counters** come from the uninstrumented sandbox jar in the same private distribution, switch on / off by
a system property in ONE binary (`work/prof/X1/ab/counters.tsv`); the census build of the sandbox
(`census-proto`) gives the probe counts. **Timings** were taken only through `bench/quiet.py` (section 5.4).

## 3. Reading the census

1. **Hash-consing pays for values and for closures, not for the tabling keys.** Probes that hit: 30-52 % overall, and
   they are concentrated: LAM closures are found again 30 % of the time on Init and the Cedar slice and absorb 63-66 % of
   their probes as hits; INFER's tabling records are found again 39-70 %. The tabling records of EVAL are the largest
   class of all (22-43 % of the records) and 82-99.5 % of them are never found again; each of them cost a PRUNE (probe
   of `rtab`, 30-90 % of the time a new frame), a probe of `vtab`, eight words of record and a VAL store.
2. **`gated` does not remove this class on the workloads that reduce.** On Init it gates 40 % of the `Eval.table`
   calls out; on the Cedar slice 32 % and on reachability 27 %, and what remains is found again as rarely as before
   (C3). One reason is in the gate's own rule: every node of an EARLIER unit's term (an unfolded definition body) is
   "reached from outside its segment" and is always tabled. On reachability s1 executes more ticks than v0 (35.40 M
   against 34.57 M).
3. **Reachability is a different regime.** 2.5 % of ALL records are ever found again; four declarations make 93 % of
   the records (sessions of 2.7 to 8 million records, intern tables of 64-256 MiB: M1's profile has 39 % of the
   process waiting for intern-table slots there). NEU 35 % of the records, 2.9 % found again; LAM 14 %, 1.3 % found
   again but 5.9 M hits on that 1.3 % (a few hot closures, hit 2,048 ticks or more after they were made). Interning
   finds little there outside a small hot set.
4. **Where sessions are large, hits are long-distance.** Of the probe hits on SUSP and FRAME records, those that come
   2,048 ticks or more after the record was made are 30-37 % on Init and Std (small sessions), 47 % on con-leche,
   56-64 % on the Cedar slice and 73-87 % on reachability (C7): a small "young" intern table in front of the big one
   would miss most hits exactly where the big one is expensive. (The second visit of a KEY, when there is one, mostly
   comes soon - the cache-size sweep of section 5.2 - but that did not turn into time.)
5. **The reuse cases of reussir are rare here, and for a reason.** Spines are built n-ary from scratch (extending an
   existing NEU makes 1.9-7.2 % of the records, and in v0 its source is always held by a memo word or an environment);
   frames are pruned from the working environment, never extended; environments are a LIFO slab (1 copy in 162 M
   pushes over all runs); Nat offsets are immediates. What reussir reuses in place - the constructor cell consumed by a
   match - is here a hash-consed NEU whose rewrite is already "in place" in the only sense the store allows: its memo
   words (`WHNF`, `UNF`, `CORE`), the thunk update of ISA section 10.
6. **Frames are sparse where environments are deep**: 75 % of the frame slots on the Cedar slice are HOLE (18 slots
   per frame, 87 % of the run words), 35 % on Init, 23 % on reachability. This is M1's open item (sparse frames), not a
   uniqueness question, but it is 54 M of the 92 M run words of the slice.

## 4. The schemes, their invariants, what breaks them, what the census says

Vocabulary of the store, as it is today (`Values`, `Runs`, `Machine`): every record is in `vtab`, every FRAME / REST
run in `rtab`, from the moment it exists (`addRecordAt` / `putRunAt` in the miss branch of the probe); ids are
positions in two bump slabs; nothing is ever removed before the session reset, which un-inserts every record and run
by re-probing. Ids are held by: spine and frame slots, the fields `a` of NEU / PROJ / NSUC / FVAR, the memo words
`m0..m3` of every kind (`VAL`, `WHNF`, `CORE`, `TYPE`, `UNF`, `DOM`, `COD`, the scope words of FVAR), the pair table
and its log, the direct-mapped caches (`CHEAD`, sort cache, literal import, `FV0`, `SIGT`, `IC`, `UNDEC`, the
closed-term memo, the APPLY memo, the REST chain cache), the OPEN bit table (indexed by id), the scope stack, the
worklist payloads, scratch `X`, the environment slab `es`, the register stack, the rule trees of `Rules`, and Java
locals of every judgment on the host stack. A record header has no free bit (kind 4 + flags 12 + aux 16); a value
ref has two reserved bits (`REF_EPH`, `REF_UNQ`).

### (a) One bit "fresh and unpublished" on the newest record: rewrite it in place before it is interned

- **Mechanism** (designed, not built). The record at `vp - 1` (and, for a NEU, its spine at the end of `rs`) is
  rewritten instead of copied: its `vtab` slot is zeroed, the words are rewritten, the new key is probed; if the new key exists the fresh
  record is popped (`vp--`, `rsp` back), else it is entered again. Zeroing the slot of the NEWEST record is a valid
  deletion in an open-addressing table without tombstones: no entry was inserted after it, so no probe sequence
  passes over its slot. This also holds after a growth, because `growVtab` / `growRtab` re-insert in id order.
- **Invariants.** F1: the id is held by nothing but the caller's operand (no slot, memo word, pair entry, cache cell,
  frame payload, scratch word, other Java local). F2: it is the newest record and its run the newest run. F3: its
  entry in the OPEN bit table is rewritten with it.
- **What breaks F1.** In v0 everything (census: the source of a spine extension is E0, i.e. held by nothing, in
  0.0 % of the cases). Where the prefix is the result of the body of a beta step that is applied further, `done` has
  just stored it as `VAL` of the body's tabling record; where it is the value of a variable, the environment holds it.
  It is unpublished only where the body is not memoised (`m2a`'s untabled bodies), and then the APPLY memo (`m2b`),
  the ephemeral memo of (e) or any other memo of the body publishes it again. Java locals cannot be audited: one
  missed holder is a value that changes under its reader, i.e. a wrong ACCEPT.
- **Census (C5).** Spine extension of an existing NEU: 1.2 % of the NEU probes on init-prelude, 5.5-11 % on the Cedar
  slice, Init, Std and con-leche, 17-20 % on reachability; the new records are 1.9 % / 3.0 % / 4.2 % / 7.2 % of ALL
  records (Cedar slice / Init / con-leche / reachability, v0); the source is the newest record in 65-73 % of them.
  Frames: a new frame whose entered source frame is never touched again, only reachable from never-found records,
  contained in the new frame and the newest run: 3.4 % of new frames on the Cedar slice, 1.0 % on con-leche, 0.5 % on
  Init, 0.4 % on reachability. NSUC made from NSUC: 6 to 878 per corpus. `PUSH` copies: 1 in 162 M pushes over all
  runs.
- **What it would save.** At best (source newest, never touched again, only reachable from never-found records) 1.3 %
  (Cedar slice), 2.0 % (Init), 4.7 % (reachability) of the records and the copy of a spine of 4 words; no probe (the
  delete replaces the insert of the prefix, the insert of the result stays), so no time is to be expected from it
  (argued, not prototyped).
- **Verdict: NO-GO.** The case is rare, the saving is memory only, and the precondition is false wherever the body is
  memoised.

### (b) An ephemeral region with mark / release per judgment, interning only on escape

Three different things hide under this name.

- **(b1) Region rollback of records and runs** (designed, not built). At a mark `(vp, rsp, plogN)`; at the return of
  the judgment every record and run above the mark that the result does not reach is dropped. Deleting ALL entries
  above a mark from `vtab` / `rtab` is valid for the same reason as in (a) (insertion order is id order, also after a
  growth), so no tombstones are needed; the cost is one probe per dropped entry, i.e. what the session reset pays
  today.
  Invariants: R1 no id above the mark survives: the result is below the mark or is copied down and re-interned; R2
  every memo word of an OLDER record that was written during the judgment and points above the mark is undone: this
  needs a write barrier and an undo log at every memo store of every package (`VAL`, `WHNF`, `CORE`, `TYPE`, `UNF`,
  `DOM`, `COD`, FVAR scope words, PROOF / PROPT bits are safe); R3 the pair entries logged since the mark are removed
  (`plog` is in insertion order: same argument); R4 every direct-mapped cache is invalidated (`epoch++`), the OPEN bit
  table is cut, NatStore ids made above the mark are released; R5 no suspended frame, scratch word or register holds an
  id above the mark (true at a judgment's return by I-STACKS, false inside a `TRY` that is cut).
  Census: of the records made inside an EVAL judgment 43 % (Cedar v0), 47 % (reachability v0) are dead when that
  judgment returns (C1: 25-43 % of all records) - but they are almost exactly the tabling records and their frames
  (C3), which `once` of (e) below never makes. Releasing costs what making cost (one probe each); what it buys is a smaller
  working set in the giant sessions (reachability: 4 declarations make 93 % of the records). **Verdict: NO-GO as a
  speed-up; keep as the v2 answer to a memory wall** (ISA section 10 already says so), and only around judgments
  whose result is a boolean (`CONV`, `PIRR`, a `TRY` segment), where R1 is free.
- **(b2) Ephemeral memo keys.** The KEY of a memo entry - the bindings a node reads - is the only thing that is
  interned for the sake of the memo alone (a frame and a SUSP record per evaluated node). Not interning it for a
  first evaluation, and in a second form holding it inline in a lossy cache cell until it would otherwise be lost,
  keeps every result exact: this is scheme (e), the one that was built.
- **(b3) Non-interned frames / closures / spines (`REF_EPH`).** A closure over a frame that is in no table, a NEU that
  is in no table. Breaks I-ID: two constructions of the same value get two ids. Conversion stays sound only if no
  judgment ever answers "different" from two different ids (by the ISA's own forms it must not today: a SUSP and its
  VAL, an NSUC and the literal it folds to are two ids of one value; I did not audit `Conv` for it), but every
  identity-keyed memo loses its hits on such values (pair table,
  `WHNF` / `UNF` memo words live in the record that is not found again, tabling keys that contain the id), the reset
  and the table growth must know which records are not in the table (the reset loop scans the whole table for a
  missing entry), and the FVAR scope protocol keys its variable by the type's id. Census: this is where the remaining
  volume is - on reachability NEU records are 35 % of all records and 2.9 % of them are ever found again, LAM
  closures 14 % and 1.3 %; on Init NEU 32 % and 15 %, on the Cedar slice 19 % and 20 %. **Verdict: v2 experiment, not
  prototyped here.** It is the real "gruszka trade" (ISA section 10, last row), it needs its own soundness review, and
  its yardstick is reachability-like closed evaluation only.

### (c) Saturating 2-bit counts in the record header

- **Mechanism.** Count the stores of an id: slot of a new run, field of a new record, memo word, pair entry, cache
  cell; a probe hit counts as a store (a second holder). 0 = held by Java locals only, 1 = one owner, 2+ = shared.
- **Invariants.** C1: every store increments before the id becomes reachable through it (one load and one store into
  a count table per slot written; in the record header it would be the random header load that M1 removed from
  PRUNE: 17.5 % of the worker on Init); C2: the count never decrements (no owner ever releases), so "1" means "was
  stored once", not "is unique now"; C3: Java locals are not counted, so "0" licenses nothing either.
- **What it could license.** In-place extension when the count is 0 (as (a), without the "newest" condition, so with a
  real table deletion); skipping a memo for unshared values (the official kernel's `is_shared` gating) - but here the
  memo words are in the record and cost nothing to keep, and the memo that does cost (the tabling record) is not keyed
  by a value at all.
- **Census.** E0 ("never found again, never stored": the count stays 0) is 36-44 % of the records, of which 75 %
  (Cedar slice) to 92 % (Init) are tabling records of EVAL and INFER (in the table on purpose, referenced by nothing
  by construction); for NEU it is 0.0 %, for LAM 1-8 %. No constructor has a population of count-0 operands to
  specialise on.
- **Verdict: NO-GO.** Nothing to specialise, a write on every store, and no free header bits (a side table like the
  OPEN bits would be needed).

### (d) Builders: assemble in registers / scratch, intern once

- **Already the design, and the census confirms it works:** spines are collected in `X` and interned with their NEU
  in one probe (the spine of an application node is never built argument by argument: `PUSH` copies 0, spine
  extensions are the application of a value that is already a NEU, 2-7 % of the records); frames are pruned from the working environment in one probe,
  without building the frame first (stage A); environments are a LIFO slab, extended in place; Nat literals are
  immediates and NSUC cells are tens to hundreds per corpus.
- **Remaining intermediates** (C2, C5): (1) the prefix NEU of an application that is extended (a closure whose body
  returns a neutral and is applied further, or a neutral variable applied): 1.9-7.2 % of the records. A builder form
  exists for the first (hand the pending arguments to the MKAPP that ends the body), but the prefix is the value of
  the body and every memo of the body stores it: it can only be skipped for unmemoised bodies. (2) the tabling record and its frame per evaluated node: 22-43 % of the records: scheme (e). (3) PII
  ("the type of this lambda"): 6 % of the records on the Cedar slice, 1-2 % found again; `expect` (M5) is the builder
  answer and removes 18 % of them on the slice. (4) FVAR per opened binder type: 5 % on the Cedar slice.
- **Verdict: nothing new to build under this heading**; (1) is NO-GO for now (small, and in conflict with (e)'s memo).

### (e) What the census points to instead: one bit per memo KEY, and an ephemeral memo in front of it

The bit of reussir answers "is this cell shared?" so that an unshared cell is rewritten instead of copied. In a
hash-consed store the cell is shared by definition; what is unshared 82-99 % of the time is the memo KEY. So:

- **`once`: one bit of visit count per tabling key**, kept outside the store in a blocked Bloom filter (two bits of
  one 64-bit word per key, at most 8 keys per word, rebuilt at twice the size from a log of the entered hashes; back
  to 64 words at the session reset). `Eval.table` asks the filter: a key that was never entered is evaluated
  WITHOUT a tabling record - no PRUNE probe, no frame, no SUSP record, no VAL store (the path that `gated` already
  uses for untabled nodes) - and is entered; a key that was entered is tabled as today.
  Invariants: O1 equal keys have equal hashes (the hash reads the term, ls' and the bindings at the mask's positions:
  the tabling key of ISA 5.1); O2 an entered key stays entered until the session reset (the log); O3 the filter
  decides only WHETHER a memo is kept, never a value: a false "seen" tables at the first visit (today's behaviour), a
  key that was tabled through a false "seen" and reads "not seen" later is evaluated once more. Consequence: a key is
  evaluated at most twice where the table evaluates it once, and a shared node of a DAG is evaluated at most twice
  per environment - the bound for which static gating needed its depth rule (M2's finding of 14:55Z: 44,030
  against 8,038,031 ticks on a dependent nest before that rule).
- **`evc`: an ephemeral EVAL memo.** Direct-mapped cells of 16 words `(term, ls', epoch, -, value, up to 11 kept
  bindings)`: the tabling key is held INLINE and compared exactly, so a hit returns what `VAL` of the tabling record
  would be, with one hash over the kept bindings and one cache line: no PRUNE, no probe of `rtab` / `vtab`. Every
  evaluation that completes on the host stack is written into its cell (`Eval.node`). With `once` behind it, a key
  gets a frame and a record only when it comes back AFTER its cell was overwritten: interning on escape, where
  "escape" is "outlived the cache".
  Invariants: E1 a cell matches only on the whole key (term, ls', epoch, every kept binding; a node with more than 11
  kept bindings or a far mask is not cached); E2 the value is never a SUSP (as for `VAL`, 2.6); E3 cells die with the
  session (epoch stamp), like the closed-term memo; E4 the bindings are read from the entry environment, which is
  intact when the node returns (I-STACKS; the put is skipped for a judgment that was suspended); E5 off under every
  debug mode that owns the hit path, and to be off in strict mode. What it changes that is observable: ticks, the
  memo contents, and the representation of some values up to PEEK (a suspension where the table had its VAL) - the
  same class of change as `gated`; verdicts and reduction results are unchanged (section 5.3).
- `prof` (a two-bit saturating counter per term node that sends nodes whose keys repeat back to immediate tabling)
  was built as the fall-back for the case that `once` alone re-evaluates too much.

Section 5 measures the three: `once` is the go; `evc` does in counters what is said here and does not pay in time
(5.4); `prof` is not needed (5.2).

### 5.1 What was built

All of it is in ONE file of the sandbox, `Eval.java` (owner M2), 298 added and 3 changed lines, behind bits of the measurement

| bit | name | what it does | where |

halves, which keeps every entered key but also keeps the SHARE of set bits, so in a large session half or more of the
answers were false "seen" (93 % in a test with 8 M keys) and the filter silently degraded to today's behaviour. It
showed as "new records at a second visit that are never found again" in the census of reachability. The fixed filter
is rebuilt from a log of the entered hashes (3.3 % false "seen" with 4 M random keys); every number below is from the

What the rows say:

- **`evc` alone changes no counter at all**: ticks, records, run words, pair entries, EVAL evaluations and memo hits
  are identical to v0 on the Cedar slice, Init and reachability. Every miss is still tabled, every hit returns the
  value that `VAL` holds; only the cost of a hit changes (section 5.4). It is also a check of its exactness: a wrong
  value would have to leave every one of these counters where it was.
- **`once` alone** removes 18 % (Cedar slice) to 41 % (reachability) of the records, but on the INFER-driven corpora it
  costs 5-6 % ticks and 10-21 % more EVAL evaluations: a key that comes a second time is evaluated a second time.
  On Init 19.4 M keys are left untabled at their first visit, 2.5 M of them (13 %) come back and are tabled then,
  and 71 % of those records are never found again (74 % on con-leche): a key is visited once, or exactly twice, far
  more often than three times - consistent with M2's observation that INFER's telescope walk evaluates an argument
  by its own ARGV and once more inside its parent.
- **`evc + once`**: the second visit is answered from the cell, so the records go and the ticks stay: Cedar slice
  -22 % records, -16 % run words, +1.0 % ticks; Init -33 %, -36 %, +0.6 %; reachability -42 %, -43 %, +0.2 %

  re-walked every time (memo hits +30 %, +65 %, +132 %). Session resets fall with the footprint (144 -> 136, 1129 ->
  1034, 53 -> 51).
- **`prof`** (the per-node counter) does what it was built for - fewer second evaluations (+0.8 % ticks instead of
  +1.0 % on the Cedar slice) - and pays for it with records (-20.4 % instead of -22.0 %). With `evc` in front there
  is nothing left for it to fix: not recommended.
- **Cache size** (`evc + once`, Cedar slice, against v0): 2^10 cells (64 KiB) ticks +2.2 %, records -21.1 %; 2^13

### 5.5 Go / no-go

"Go" means: worth handing to the owner as a staging switch, on the evidence of ONE worker on the JVM launcher.

| Scheme | Verdict | Why (census / prototype) |
|---|---|---|
| (a) one bit "fresh and unpublished" on the newest record, in-place extension / pruning | **NO-GO** | the cases are 1.9-7.2 % of the records (spines) and 0.4-3.4 % of the new frames; in v0 the source is always held by a memo word or an environment (E0 in 0.0 % of the cases); a rewrite saves bytes, not a probe (argued, not built) |
| (b1) region rollback per judgment (mark / release of records and runs) | **NO-GO as a speed-up**, v2 if a memory wall is measured | releasing costs one probe per record, as making did; it needs an undo log at every memo store and a flush of every id-keyed cache; what it would release is what (e1) never makes (not built) |
| (b3) non-interned NEU / closures / frames (`REF_EPH`) | **not prototyped: v2 experiment**, yardstick reachability | it is where the remaining volume is (with `evc + once` NEU are 59 % and LAM closures 23 % of the records on reachability, 3.5 % and 1.3 % found again), but it gives up I-ID and every identity-keyed memo on those values; needs its own soundness review |

## 7. Not established

- **Parallel workers.** Every number here is one worker. The owner's metric is warm wall clock with 8 workers; the
  filter is a per-worker array, so nothing is shared, and the saving on reachability is cache traffic that 8 workers
  compete for - which may make it larger or smaller; not measured.
- **The native image.** All runs are the JVM launcher (C2). The integration log has the native image at 0.5-0.9x the
  CPU time of the JVM launcher on Init, Std and the Cedar slice; the relative gain there is not known.
- **Steady state, and small effects.** A process checked the export 2 or 3 times; the last pass is the warmest one
  measured, not a proven steady state. Rows have one to seven processes; on the Cedar slice and on Init against v0
  the effect of `once` is inside the spread (section 5.4), so "no resolved change" is not "no change".
- **Timing on the newest tree.** Every timing is the build of 15:09Z. On the main tree as copied at 16:53Z (which runs
  `gated,expect,warm` with a 1 MiB cap by default) only counters were taken: Cedar slice +5.3 % ticks / -15.6 %
  records, reachability +0.4 % / -37.6 %.
- **The large corpora** (mathlib, cslib, navier-stokes-euler, full cedar): not run. Std and con-leche: counters of
  `once` only, no timing.
- **M8's full gate with the switch** (tier and convention equivalence, mutants, audits, the 230 tests through the
  driver): not run. The differential run over all 230 tests with `evc + once` was stopped by me after 15 minutes in
  the heavy perf files (at least 200 of the 230 files were done; no report was written, so it is no evidence).
- **Why exactly `evc` costs 7-10 %.** The prototype computes the node mask and the key hash up to three times per
  evaluated node and writes a cell per evaluation; a leaner form may pay, but nothing here shows that it would.
- **(b3), non-interned NEU / closures**: only its census bound is known (section 4); no prototype.
- **Reads through Java locals** are invisible to the census: "dead at return" is an upper bound (section 1).
