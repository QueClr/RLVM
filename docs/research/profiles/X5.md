# X5 - proofs read lazily from the file: analysis, prototype, recommendation

Scout X5, 2026-11-24. Question: the loader is one thread and the floor of a pipelined run (mathlib: 12.4 s
native `-O3` after wave 7; 11.3 s wall with two scanner threads before it). On exporter output the proof-only
records of a theorem are an id range that is recognisable without parsing them (finding F1). Can the loader
leave those byte ranges in the file and the worker that checks the theorem parse them itself?

Everything here is outside the published modules: private copies and a private build under `work/prof/X5/`
(`build.sh`, javac, nothing installed), two simulations on the published reader, a prototype on the real store.
Living summary: `work/status/prof-X5.md`.

## 0. Result

**It works and it agrees with the eager loader, but it buys much less than F1 suggested. The serial load gets
1.6 to 1.75 times faster (not five times), the workers pay 3 to 5 times the block decode for it, and today the
wall clock of a pipelined run gets worse, not better.**

| | Init | Std | cedar | mathlib |
|---|--:|--:|--:|--:|

| bytes left to the workers | 76.9 % | 72.1 % | 71.1 % | 68.7 % |
| **load phase, one thread, eager -> lazy** (JVM, warm) | **0.52 -> 0.32 s** (x 0.61) | **0.93 -> 0.53 s** (x 0.57) | **1.43 -> 0.92 s** (x 0.64) | **10.64 -> 6.35 s** (x 0.60) |
| **proofs decoded by 8 workers, CPU, blocks -> ranges** | **0.16 -> 0.51 s** (x 3.2) | **0.23 -> 0.92 s** (x 4.0) | **0.31 -> 1.65 s** (x 5.3) | **2.65 -> 9.58 s** (x 3.6) |
| - of that, the foreign records | 0.27 s | 0.52 s | 1.08 s | 4.74 s |
| load + decode, CPU | +23 % | +25 % | +47 % | +20 % |

(JVM C2 with the launcher's flags, quiet cores, medians of warm passes; mathlib one run. Sections 1 to 5.)

1. **The rule holds and needs five guards.** A `thm` whose value is the last expression record of its segment and
   whose type is an earlier record: the records after the type are the proof. The loader keeps 18 - 28 % of the
   expression records, all names and levels, and still looks at the first bytes and the end of every line. On
   18,005 small files (230 arena tests, 17,775 mutants) and on Init, Std, cedar and mathlib the lazy load gives,
   for every constant, the same type and value as the eager load, or fails with the same message, or restarts
   (309 files). Without the binding guard 14 `reorder_decl` mutants load differently (sections 5.5, 6).
2. **Foreign records are the expensive part.** 5.5 - 6.9 % of the references of proof records go to a proof record
   of an earlier theorem that no shared record needed. Served by the worker from the file (binary search over
   28-byte range rows, interpolation on the bytes, memo per declaration) they are 16 - 23 % more nodes and half
   or more of the worker's decode time (280 - 315 ns each). A table shared by the workers would halve their
   number; parsing whole ranges on first use would parse 83 - 94 % of everything again (section 2).
3. **The serial part does not shrink with the record count.** Pass one over every line (4.0 - 4.3 GB/s), names,
   levels, declaration rows, page faults and the shared prefix stay. Measured lazy / eager: 0.57 - 0.64
   (0.60 on mathlib: 10.6 s -> 6.4 s on the JVM); projected from the published profile of the native
   load of mathlib: 12.4 s -> 7.3 s, 5.7 s if a scanner thread takes pass one (section 3).
4. **End to end** (section 5.6): under pipelining wall = max(serial loader, checking). With the machine's check
   phase of today (8 workers, quiet cores: Std 1.85 s, cedar 2.26 s, mathlib 42 s) checking is the larger term
   everywhere, so lazy ranges only add worker time: Std +6 %, cedar +8 %, mathlib +3 %. They win
   once the check phase is shorter than the eager load, i.e. with checking 1.9 (Std), 1.6 (cedar), 3.9
   (mathlib) times faster than today, and then by at most 36 - 43 % of a loader-bound wall clock. In the
   check-only reading of "warm" (`-X passes=N`, later passes do not load) they can only lose.

**Recommendation: NO-GO now; keep the design and the prototype for the day the loader is the floor.**

- Nothing of this should enter `rlvm-load` / `rlvm-store` / `rlvm-driver` while the check phase is longer than the
  load on the corpora that count. The switch point is measurable with numbers the team already produces: check
  phase with 8 workers against `stop-after=load`. Std and cedar are within a factor of two of it, mathlib a
  factor of four.
- If it is built then, build it as section 7 says: a range is a proof block whose records are still text (no
  consumer of `Overlay.blockRoot` changes), restart instead of guessing, only ACCEPT final under lazy loading,
  and variant B for the foreign records; and cost the variant of section 7.5 first (scanner threads pack the
  ranges: no text in the workers, no second read, no restart). Size of the prototype: reader side 1,300 lines, loader sink
  350, store decoder 600; to that come the publication of `loc` and of the range rows, the driver's restart rule
  and a mutation campaign aimed at ranges.
- The cheaper step toward the same floor, which needs no new trust argument: `-X load=pipelined` with
  `-X scan-threads=2` as the default (the load path owner's proposal of 14:35Z; -21 % wall of the load, measured
  by them). Pass one is context-free, so the same scanner threads could classify and count for a lazy mode later.
- By-products usable now: `X5Tool diff` (structural digest of every constant of two loads of one file; it found
  the binding difference in minutes) and the measured unit costs for anybody who wants to cost another split:
  line end + class 13 ns per line, template tokenising 28 - 32 ns per record (1.7 - 2.0 GB/s), node write 20 - 35 ns,
  block decode 28 - 34 ns per node, a record fetched at random from the file 280 - 315 ns.

## 1. The rule

F1 (first half of this scout, `work/prof/X5/sim/LazySim.java`): lean4export writes the records a declaration needs
right before its declaration line, children first, the type's records before the value's. With ids dense and in
file order, at a `thm` / `opaque` line with type id T and value id V the records of the segment with id <= T are
what the type reaches and the records with id in (T, V] are the proof-only records; V is the last expression
record of the segment. The eager loader finds the same split by parsing everything and marking what the type
reaches.

The guarded rule that the prototype implements (and section 6 proves equal to the eager split):

> A unit is **lazy** iff the reader has seen names, levels and expressions with ids 0, 1, 2, ... in file order so
> far, every line of the segment starts like a name, level, leaf, structure, projection or declaration record,
> the declaration line is a `thm` in template form, its value id V is the id of the last expression line of the
> segment, and its type id T is smaller than V. Then the **prefix** is the expression lines with id <= T and the
> **range** is the rest. The loader parses all name and level lines of the segment, the prefix, the **leaf lines
> of the range** (`const`, `sort`, `bvar`, literals: they need the loader's name, level and literal tables) and
> the declaration line. The **structure lines of the range** (`app`, `lam`, `forallE`, `letE`, `proj`) stay in the
> file; the loader records `[first ordinal, record count, file offset, byte length]` of the range and nothing per
> record.

Simulation of exactly this rule on the published reader (`work/prof/X5/sim/LazySim2.java`,
`work/prof/X5/data/lazysim2-*.txt`; `thm` and `opaque` units; the prototype takes `thm` only, hence its slightly
smaller numbers in section 5):

## 2. Foreign records: how to serve them (question a)

A structure record of a range refers to: its own range 61 - 64 %, its own prefix 0.5 - 1.7 %, a shared term
28 - 32 %, **a structure record that an earlier range left in the file and that no shared record ever needed
("foreign") 5.5 - 6.9 %**, a record of a proof block 0 (2 to 12 references per export, into the one ownerless
block). The eager loader sees every such reference and promotes the target; the lazy loader does not, so a
worker has to get the record, and what it reaches among such records, from the file.

| ranges with any foreign record | 27,972 of 37,600 | 48,948 of 64,516 | 54,728 of 73,305 | 15,276 of 20,093 | 309,338 of 475,131 |

| - earlier ranges entered (per declaration with any) | 197,761 (7.1) | 323,937 (6.6) | 394,425 (7.2) | 183,575 (12.0) | 2,473,720 (8.0) |

(percentages of A and B: of the structure records left in the file.)

**The index.** The record id is written in every line and the ids of a range are dense, so no per-record index is
needed (4 bytes per record would be 310 MB on mathlib): the range of an ordinal is a binary search over the first
ordinals of the ranges (mathlib: 475,131 ints = 1.9 MB, 19 steps), the line is found by interpolation on the bytes
of the range and a short walk (`RangeFile.find`): measured 1.02 - 1.07 interpolation probes and 2.4 - 2.5 lines
walked per record; a child of a foreign record is searched from its parent's position (usually a few lines back).
Every answer is verified against the id in the line (section 6, W5).

**Cost, measured** (prototype, variant A; the same decode run with the foreign references replaced by a
constant, section 5.3): Init 0.27 s of CPU time for 0.96 M records (279 ns each; 53 % of the whole decode);
Std 0.52 s of CPU time for 1.85 M records (280 ns each; 56 % of the whole decode);
cedar 1.08 s of CPU time for 3.42 M records (315 ns each; 65 % of the whole decode);
mathlib 4.74 s of CPU time for 15.33 M records (309 ns each; 49 % of the whole decode).
The search itself is probably not what costs (replacing its per-byte reads by 8-byte steps changed nothing
measurable); the likely cost is memory latency: the line, the range rows, and above all the shared children of
the record, scattered over the export region, which the eager design pays on the loader thread when it promotes.
Not profiled.

**Assessment.**

- **A (prototype)** needs nothing shared and nothing concurrent, and costs as much as the worker's own range or
  more (49 - 65 % of the decode).
- **B** would parse 2.2 - 2.8 times fewer records (mathlib 8.36 M instead of 18.29 M: about 2.6 s of
  CPU time less at the measured unit cost) and gives the records shared ids again, which every table keyed by
  shared id (facts, warm sessions) likes. It needs what the store does not have today: a region written by
  several workers (a compare-and-set slot per ordinal, nodes published before the slot; 32 bytes per node:
  mathlib 268 MB, less than the 317 MB of the eager loader's 9.9 M promoted copies). The binding guard of
  section 6 is what makes such a node independent of the worker that builds it. Worth building only together
  with the rest.
- **C** is no option: the ranges that some later proof enters hold 83 - 94 % of the records, so "on first use"
  means parsing nearly everything a second time, serialised on a lock per range.
- A second pass of the loader cannot help: it would have to parse the ranges to learn the references.
- The loader's own promotion on demand (a shared record refers into a range: 1.7 - 2.7 % of the records left) uses
  the same search and is in the measured load times.

## 3. What the loader's serial part becomes (question b)

**It still looks at every line.** The loader learns the kind of a segment only at its declaration line, and the
name and level records that lie inside ranges (25 - 45 % of all name records) are its own business, so it needs
the start and the first bytes of every line. What it saves is the tokenising of the structure lines of the
ranges and everything the sink does with them (segment record, block record, promotion). The number of
expression lines of a segment gives the range without tokenising them: the range is the last `V - T` expression
lines, and "V is the id of the last expression line" is a count of line starts.

Measured on one thread (JVM C2, warm; `X5Tool scan` / `reader`; section 5.1): copying the mapped file through the
reader's buffer 18 - 30 GB/s; one newline search per line 4.4 - 5.1 GB/s; the class of every line from its first
bytes plus the newline search **4.0 - 4.3 GB/s (13 ns per line)**; the template scanner on every line (reader
alone, null sink) 1.7 - 2.0 GB/s; the lazy reader alone 2.3 - 2.6 GB/s. A `memchr`-speed pass exists only for
the copy; the per-line floor in this code base is the eight-byte-step newline search, which the classification
(one load and compare per line) raises by 10 %.

| Loader thread, lazy | bytes | records |
|---|---|---|
| pass one: line ends and classes | all (mathlib 6.33 GB: 1.47 s measured) | none |
| names and levels | their lines | all (mathlib 4.3 M) |
| expression records | prefix lines, lines of eager units, leaf lines of ranges: 23 - 31 % of the bytes | 18 - 28 % (mathlib 29.6 M of 107.0 M) |
| declaration lines | all | all (mathlib 721,845 units) |
| promotion on demand | random access into ranges | 1.7 - 2.7 % of the records left (mathlib 2.07 M) |
| not done any more | - | 72 - 82 % of the segment records, all block records (mathlib 78.2 M, 361 MB), 79 % of the promotions (mathlib 9.9 M -> 2.1 M), the writes of `loc` for the ranges |

**Expected load time of mathlib from the published profile** (`rlvm-load/README.md` "Wave 7", `rlvm-store/README.md`
"Wave 7"; native `-O3`, final figure 12.40 s, `work/status/rlvm-load.log`): reader 22 % = 2.7 s, kernel (page
faults) 11 % = 1.4 s, `Loader.exprApp` 12 % = 1.5 s, promotion 10 % = 1.2 s, `NodeCtx.writeApp` 8 % = 1.0 s, names
7 % = 0.9 s, block writer and `ref` 8 % = 1.0 s, the rest 22 % = 2.7 s. Lazy: reader 1.6 s (pass one) + 0.31 x 2.7 s
= 2.4 s; page faults of the input stay, those of blocks, memo and three quarters of `loc` go: about 1.0 s; names
0.9 s; `exprApp` x 0.28 = 0.4 s; node writes x 0.82 (31.7 M instead of 38.7 M export nodes) = 0.8 s; promotion from
the file, 2.07 M records at 0.3 us = 0.6 s; block writer 0; the rest x 0.45 = 1.2 s. **Sum 7.3 s, 59 % of the
eager load**; with pass one on a scanner thread 5.7 s. The prototype measures the same ratio (section 5.1):
0.57 - 0.64 on Init, Std and cedar, 0.60 on mathlib.

**Why not a fifth.** F1 counted records. The sink's time is not proportional to them: names, levels,
declaration rows and page faults do not shrink, the reader has a per-line floor, and the 18 - 28 % of the
records that stay are the shared ones, whose nodes are the expensive ones to write (derived facts, children in
a region far larger than the caches).

`work/prof/X5/`, built by `work/prof/X5/build.sh` (javac into `work/prof/X5/classes`, against the installed
`rlvm-level` / `rlvm-nat` jars; nothing is installed). 2,950 lines new, 350 lines changed in `Loader`.

What the prototype is not: it is a batch load (the workers decode after the load, so nothing is published
concurrently); `opaque` records are loaded eagerly; the theorem's value word in the store is 0 for a range (the
range table is beside the store); no engine runs on it. Its store is compared with the eager store instead
(section 5.5).

## 6. Soundness: what is verified, by whom, and what happens to a file that is not exporter output

The eager path stays as it is and decides every file the lazy path does not take. The lazy path can only
ever contribute an ACCEPT; the argument has to show: *lazy ACCEPT implies eager ACCEPT*.

### 6.1 What the loader thread verifies before it leaves anything in the file (per unit, at the declaration line)

L1. The reader is in the state "ids are 0, 1, 2, ... in file order" for names and levels and "dense without a
    table" for expressions, since the start of the file (`IdSpace.denseInOrder()` / `dense`). Lost once = lazy
    mode ends for the rest of the file; lost after expression lines of the open segment were classified = restart.
L2. Every line of the segment starts like a name, level, leaf, structure, projection or declaration record
    (`Lines.classify`: the first 8 bytes; for `{"ie":N,` the 8 bytes after the number). Any other first bytes
    (`mdata`, whitespace, another key order, CRLF, a blank line): lazy mode ends, the open segment is parsed
    eagerly in file order.
L3. Every line the loader parses itself is what its first bytes say: a NAME / LEVEL line binds exactly one name /
    level and nothing else; a run of n expression-class lines binds exactly n expression ids and no name or
    level; a leaf-class line inside a range gives exactly one leaf record (the sink refuses a structure record
    there). Otherwise restart. (Needed because the names and levels of a segment are read ahead of its
    expression lines; with L3 that reordering is not observable, and "defined before use" stays exact: while an
    expression line is parsed, exactly the names and levels of the lines before it are visible, `IdSpace.show`.)
L4. The declaration line is a `thm` in template form, its value id V is the id of the LAST expression-class line of
    the segment (first id of the segment + number of expression-class lines - 1), its type id T is smaller than V.
    Else the unit is loaded eagerly.
L5. Binding guard, after the theorem's name is claimed: every record of the range that names something is
    resolved NOW: the CONST leaves are bound with the right number of levels, the literal leaves have their
    prerequisites, every projection names a declared structure (`LoadTarget.unresolvedRefs`, `isUnresolved`,
    `isDeclared` in the prototype). Else restart.

What the loader has then parsed, exactly as the eager loader parses it: all names and levels, the expression
records with id <= T (the prefix; the usual mark / sweep: reached by the type -> shared, not reached -> the
unit's proof block, which then is ownerless), the leaf records of the range, the declaration line.
What it has NOT looked at beyond their first bytes and their line ends: the structure lines of the range.

### 6.2 What the worker verifies when it parses a range (`RangeDecoder`), before the unit can be accepted

W1. The range's bytes end with a newline and split into lines each of which is, for the same classifier and the
    reader's own template scanner: a name line, a level line, a leaf line (these three were parsed completely by
    the loader, L3), or an application / lambda / forall / let / projection **in exact template form, byte for
    byte**. Anything else: restart.
W2. The k-th expression line of the range carries the id `first + k` (so the ids of the range are dense, in order,
    not repeated), and the number of expression lines is the number the loader counted.
W3. Every reference of a structure record goes to an expression id smaller than its own (defined before use, as
    the reader requires); every binder name and structure name is a name id smaller than the number of names
    defined before that line (names before the range + name lines of the range seen so far).
W4. A projection index is at most 2^31 - 1 (the eager loader declines above it); the projection was announced by
    the loader (its structure name translated on the loader thread).
W5. A reference to an earlier record without a location (a "foreign" record, in the range of an earlier theorem)
    is served by parsing that one line: it is found by id inside the byte range the loader recorded, starts after
    a newline, is in template form, carries exactly that id, refers only backward. A reference to a record of a
    proof block the loader wrote (ownerless blocks, eager theorems, opaques) decodes the block, and restarts if
    the block has an unresolved record (`ProofBlocks.hasUnresolved`): the eager loader would have promoted the
    record and bound it again for this unit.

### 6.3 Why the result is the eager loader's

1. *Same records.* By L1-L3 and W1-W3 for every range, the eager reader reads the same file in dense mode and
   delivers the same records with the same ordinals; nothing it would reject or decline is present in a parsed
   range (W1-W4 are the reader's and loader's own conditions on such lines; any line that needs the general
   JSON path restarts instead of being interpreted).
2. *Same split.* With dense ids in file order a record refers only to smaller ids. So nothing reachable from the
   type T has an id above T, and every record of (T, V] is unmarked for the eager loader: its block is exactly
   the unreached records of the prefix plus the range. The lazy path keeps the unreached prefix records in a
   block and the range in the file; the value is record V in both.
3. *Same promotions.* A shared record of a later unit that refers into a range (a later declaration's type that
   uses a proof record, a definition that shares a subterm with an earlier proof) is the eager loader's
   promotion: the lazy loader parses the record and what it reaches among records without a location from the
   file at that moment (W5's checks) and writes the same shared nodes. It promotes less only because it does not
   see the references that proof records make; those are the foreign records of W5, which the worker builds as
   overlay nodes.
4. *Same bindings.* The eager loader binds a block record when the theorem is declared and a promoted copy when it
   promotes it. By L5 every name-bearing record of a range is bound at the theorem's declaration; a name is
   declared once (a second declaration is the loader's rejection); so the record denotes the same constant
   whenever and for whomever it is materialised. Without L5 this fails: 14 `reorder_decl` mutants (section 5.5).
5. *ACCEPT needs every range parsed.* A unit is accepted only after its worker parsed its range (W1-W5 hold for
   it); a run is accepted only if every unit is. So at ACCEPT every range of the file has passed W1-W5, the
   loader finished without a restart, and by 1-4 the eager store is isomorphic to what was checked (per constant:
   the same type and value up to term ids). A foreign line read by an earlier-finishing worker belongs to a
   range whose own worker validates it before the run can be accepted.

### 6.4 The rules that make it exact

R1. **Restart, never guess.** Any failure of L1 (after the fact), L3, L5, W1-W5, and any `LazyRestartException`
    of the loader's promotion on demand, ends the lazy run: every outcome obtained so far is discarded and the
    file is read again by the eager path (which then rejects, declines or accepts it as today).
R2. **Only ACCEPT is final under lazy loading.** A REJECT or DECLINE reached while ranges are unparsed is not
    exact (an earlier bad line may sit in a range nobody parsed; a message and line number would differ; a
    loader rejection assumes the ids of the skipped ranges): the run is repeated eagerly. Failing runs pay one
    extra load; they already pay a second check of the failing unit in pipelined mode.
R3. **Every range is parsed before ACCEPT**, also the range of a unit whose value an engine never asked for: the
    store keeps a "validated" bit per range, the board accepts only when all are set (a worker validates the
    rest at the end: tokenising alone runs at 1.7 GB/s per core).
R4. The export must not change during the run (it is read twice). The eager path has the same assumption for
    the one pass it makes; it is stated here because a change between the two reads is not detected.

### 6.5 Hostile and mutated files against the rule

| File property | What happens |
|---|---|
| ids not dense / not in order (880 `renumber_ids`, sparse ids, ids >= 2^63) | L1: never lazy, or lazy until the first such line |
| ids not dense INSIDE a range (a structure line with another id, an id twice) | W2: restart |
| a shared record refers into a range; a later type or definition uses a proof record | promotion on demand from the file (6.3.3); 1.7 - 2.7 % of the records left on exporter output |
| value is not the last record of its segment; type id >= value id; value is an earlier record | L4: the unit is eager (141 + 2 units in the mutants; 52,306 theorems and opaques of mathlib have an earlier record as value and no range) |
| prefix record not reached by the type (records written early, `drop_decl`, `reorder_decl`, `swap_child`: 117 units) | the record goes to the unit's block as today; a range that refers to it decodes the block (W5) |
| a proof names a constant that is declared later (`reorder_decl`, `drop_decl`, `swap_name`, `forge_flag`) | L5 / W5: restart (219 mutants) |
| a structure line of a range uses a name or expression id defined later | W3: restart (3 mutants) |
| `mdata`, reformatted JSON, CRLF, blank line | L2: lazy mode ends at that line (`wrap_mdata`: 2,238 of 2,802 files leave it at their first `mdata` record; `reformat_json`: 875 of 880 files have no range at all) |
| a line that starts like one kind and is another | L3 (loader side), W1 (worker side): restart |
| a record dropped or duplicated (`drop_record`, `duplicate_record`) | the reader's rejection on the loader thread, or restart when the id spaces lose their order after expression lines were classified (87) |
| a segment above 1 GiB | lazy mode ends there (the segment buffer is bounded); long lines are no problem (mathlib has one of 2.7 MB) |

Evidence (section 5.5): the prototype against the eager loader on 18,005 files and on Init, Std, cedar, mathlib.

## 7. The design, for the owners

Terms as in `rlvm-load/README.md` ("What the loader does", "Pipelined loading"), `rlvm-store/README.md`
(proof blocks, decoder, frontiers) and `rlvm-driver/README.md` ("Per unit", "Pipelined loading").

### 7.1 rlvm-export (reader)

- `LazyRead` (prototype: `work/prof/X5/rlvm-export/.../LazyRead.java`, 556 lines): a third mode next to
  `sequential` and `ParallelScan`, chosen by `ExportReader.Options.lazy` when the sink is a `LazySink` and the input
  is mapped. Per segment: pass one classifies every line (`Lines.classify`) and finds its end, parses name and
  level lines at once; at the declaration line the rules L1 - L4 decide; pass two parses the prefix (or the
  whole segment) in file order; the range is announced with `lazyBegin / lazySkip(n) / lazyProj(name, index) /
  lazyEnd(fileOffset, byteLength, count, ..)`, its leaf lines are delivered as ordinary `expr*` calls.
- `IdSpace.show(n) / showAll()`: visibility of names and levels while the expression lines of a segment are
  parsed after its name lines (exact "defined before use"), in dense and in table mode (the real store numbers
  names itself, so names are in table mode from the first special name on).
- `Lines.RangeScanner` + `RangeOut` (public): the template scanner for the workers; `RangeFile`: one record of a
  range by id (interpolation on the bytes, then a short walk; every answer verified against the id in the line).
- For `ParallelScan` (scan threads): the classification is context-free, so pass one can run on the helper
  threads per 4 MiB chunk (line starts + classes + the tokens of name / level / leaf / declaration lines and of
  the lines up to T); a segment that crosses a chunk border is tokenised completely, as today. Not built. It
  takes pass one (23 - 27 % of the lazy load in the prototype) off the sink thread.
- `opaque` records need the two ids from the general path (the template scanner has no `opaque` shape); the
  prototype loads them eagerly (0.4 - 1.3 % of the ranges of section 1).

### 7.2 rlvm-load (loader)

- `Loader implements LazySink` (prototype: 350 lines added to a private copy). State per range, nothing per
  record: `LazyRanges` = first ordinal, record count, file offset, byte length, names defined before, owner cid,
  structure count (28 bytes per range: mathlib 475,131 ranges = 13 MB) and, per projection record left in the
  file, (ordinal, store name id) (8 bytes; mathlib 18,818), because only the loader thread can translate a name id.
- `loc[ordinal] == 0` now also means "left in the file" for an ordinal below the segment (today it never is 0
  there). `resolvePending` / `rootRef`: `l < 0` promotes from a block as today, `l == 0` promotes from the file
  (`lazyPromote`: range by binary search over the first ordinals, line by `RangeFile.find`, children first, no
  recursion, same `LoadTarget.app / lam / pi / let / proj` calls as the sweep). `loc` of a range is not written at
  all (mathlib: 310 MB of the 428 MB stay untouched).
- The leaf records of a range are written as shared nodes at the theorem's declaration (after the claim, so
  they bind as the block record would). The binding guard L5 is what makes this the eager loader's node.
- The theorem's value: the range (new value word, 7.3) unless V is a leaf (then the shared term: 33 / 86 / 122 units
  on Init / Std / cedar).
- New in `LoadOptions`: `withLazyRanges(boolean)` (off for `withProofBlocks(false)`), `withLazyMinRecords(n)`;
  `LoadReport`: ranges, bytes and records left, leaves, promotions from the file. `ExportLoader` lets
  `LazyRestartException` through as a third outcome ("read again eagerly"), not a verdict.
- Pipelined mode: the range rows, the projection rows and `loc` have to be published with the frontier (today
  `loc` is the loader's private array): the workers read `loc` for every reference of a range to an earlier record.
  Rule for a reader on frontier n: a location above the export end of that frontier (a promotion made for a
  later unit) counts as 0, i.e. the record is parsed from the file. `loc` has to stop moving when it grows
  (chunks), or be handed over like the other published arrays.
- `MalformedExportException.line()`: the loader derives the line from its record counters; with skipped records
  that still holds (ordinals advance), but an error inside a range has no loader line: by R2 the eager rerun
  reports it.

### 7.3 rlvm-store

- **A range is a proof block whose records are still text.** `ProofBlocks` gets a second row kind: file offset,
  byte length, first ordinal, record count instead of chunk and position; `DeclTable.value(cid)` stays
  `-(block + 1)`. Then `Overlay.blockRoot(block)`, the block map, `mark / resetTo / reset`, `nodeCount(block)` and
  every consumer (`rlvm-machine` `Decl` / `Reduce`, `rlvm-ref` `RefKernel`, `rlvm-admit` `StructuralChecks` /
  `OfficialOrder` / `EnvBuilder`, the test kit) work unchanged; `hasUnresolved(block)` is false for a file block by
  L5. The prototype does exactly this inside the overlay (`RangeDecoder.decode` ends with `commitBlock`).
- `ProofBlocks.decode` dispatches on the row kind to the range decoder (prototype: `rlvm.store.RangeDecoder`, 602
  lines, same `NodeCtx` writers and the same sharing-flag rule as `decode`). It needs the mapped export
  (`Store.attachExport(MemorySegment)`), the published `loc`, the range and projection rows, and the template
  scanner: either `rlvm-store` depends on `rlvm-export` (as the prototype's private copy does; the store's own
  rule today is "nothing but the JDK"), or the scanner is handed in through a small interface.
- Promotion from the file as a store operation (`StoreBuilder.promoteRecord(kind, children..)` setting `F_SHARED`
  like `promote` does; the prototype uses the plain appends, whose flags come from the open unit only).
- Memory: no block bytes (mathlib 361 MB), no promotion memo (up to 313 MB), no sparse record index; the export
  region ends smaller (mathlib 38.7 M -> 31.7 M nodes). In exchange the export stays mapped and its pages are
  read a second time, by the workers (section 8).
- Optional, for check-only passes (`-X passes=N`) and re-checks: keep the packed form of a range after its first
  decode (write the block bytes then), so that only the first decode pays for text.

### 7.4 rlvm-driver (P7)

- Nothing in `Worker`'s per-unit flow if the store hides ranges behind block indices.
- **Restart** (R1): a `LazyRestartException` from the loading thread or from any worker cancels the run like an
  `Error` in the loader does today (checking threads joined, outcomes discarded), then `execute()` runs once more
  with lazy ranges off. Statistic `driver.lazy.restarts`.
- **Verdict** (R2, R3): with lazy ranges only ACCEPT is recorded as final, and only when every range is
  validated; anything else reruns eagerly. This composes with the existing rule "nothing but an ACCEPT is recorded
  for a unit that started before the end of the load".
- Scheduling: the frontier advances about 1.6 - 1.75 times faster, a theorem costs its worker 10 - 19 us more on
  average (section 5.3); `-X scan-threads` can take pass one.
- `-X lazy-ranges=on|off` (default off until the gate is green in that mode), in `rlvm-main` / `MainOptions`.

### 7.5 If the worker price is the obstacle: let the scanner threads pack (not built, not measured)

Pass one is context-free, so a scanner thread can do per chunk what `RangeDecoder` does per range, without the
store: tokenise the structure lines of a range and write them as block records whose references are still
ordinals (own range: back distance; earlier record: its ordinal). The sink thread then appends the bytes of that
block and never sees its records; a worker decodes an "ordinal block" with one `loc` read per reference to an
earlier record, and fetches a foreign record by index from the earlier block instead of searching text. From
the measured terms: the sink thread's time is the lazy load without pass one (last row of table 5.1); the
worker's time for its own range is about the "without foreign records" row minus the tokenising (Init 0.09 s,
Std 0.16 s, cedar 0.23 s: less than today's block decode, because the leaves are shared nodes already), plus the
foreign records at a lower unit cost than from text. Every line is then parsed during the load, by the reader's
own code and with its own verdicts, so the restart rule, the second read of the file and the dependence on the
page cache disappear; the binding guard, the published `loc` and the foreign records remain. It needs two
scanner threads that compete with the workers while the file loads (tokenising mathlib's ranges is 2.1 s
of CPU time). If the loader ever is the floor, this variant should be costed before the text one is built.

## 8. What was not established

- **Native image.** Every time here is JVM C2 with the launcher's flags. The target platform's load is 12.4 s for
  mathlib (native `-O3`), where `Mem.u64` and `Scanner.num` are out-of-line calls (22 % of the load is the reader):
  pass one and the workers' tokenising use the same primitives, so both sides of the trade may be slower there.
  The ratio lazy / eager is what should carry over; it was not measured.
- **Pipelined operation.** The prototype decodes after the load. Not measured: workers and loader running
  together (memory bandwidth: the loader writes the store while eight workers read 4.3 GB of text), the
  publication of `loc` and of the range table, the frontier rule for late promotions (7.2).
- **How often a proof is decoded in a real run.** Admission's structural checks and the engine call
  `Overlay.blockRoot` on the same worker overlay (`WorkerContext.overlay`), so normally once per unit; a session
  reset between the two, a re-check and every later pass of `-X passes=N` decode again. There is no counter. The
  worker price of section 5.3 is per decode.
- **The page cache.** The lazy run reads the export twice, the second time at random from eight threads, up to
  the end of the run. All measurements had the file in the page cache (the mathlib run was preceded by a `cat`).
  On the arena's 16 GB runner mathlib's 6.3 GB of file pages compete with the store; if they are reclaimed the
  workers wait for the disk. The eager loader drops the pages behind it (`unloadMapped`).
- **Scanner threads together with lazy ranges** (pass one on helper threads): estimated from the measured pass
  one, not built.
- **A table shared by the workers for foreign records** (variant B of section 2): counted, not built.
- **`opaque` units**: loaded eagerly by the prototype (0.4 - 1.3 % of the ranges of the simulation).
- **mathlib**: one run, no repetition (a first attempt at 16:24Z measured nothing: the tool's newline
  micro-measurement looped on mathlib's 2.7 MB line and held the measurement lock for 270 s before it was killed;
  fixed and tested on a synthetic export with 3 MB lines, `work/prof/X5/testdata/`); con-leche: simulation only.
- **Files that change while they are read**, and exotic inputs beyond the 18,005 files (the generators of
  `rlvm-testkit` were not rerun with new mutation kinds aimed at ranges: a structure line with a foreign id, a
  range line with trailing bytes, a leaf-class line that is a structure record). The checks W1 - W3 and L3 are
  written for them and three of the 309 restarts come from W3, but a campaign that targets the range rule
  directly is owed before this could ship.
