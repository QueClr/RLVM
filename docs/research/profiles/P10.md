# P10: where a warm Mathlib pass goes - itemized

Profiler "P10", 2026-11-24, 22:15Z to 23:50Z. The project owner's question, on the two warm wall clocks of one pass
over all of Mathlib with the machine engine and 8 workers (`work/status/machine-integration.md`, wave 6):

> "27.4 s (21.2 s on the JVM): do you have itemized cost: gc, hash consing, num computation, etc."

This report is that itemization: ONE table (section 0), in seconds of wall clock and in CPU seconds, for the JVM
launcher and for the native image, every sampled method assigned to exactly one item by a published file
(`work/prof/P10/items.map`), so that the table can be re-made after the next change (section 7). No code was
changed or published. Living summary: `work/status/prof-P10.md`.

## 0. Answer

Same export (`work/exports/mathlib.ndjson`, 6.33 GB, 721,845 units), same jars (published 22:18Z; machine
`df36be3c8cc9`), `-X engine=machine` with its default switch set, 8 workers, load pipelined with checking, a warm
pass of `-X passes=N` on the 8 quiet measurement cores. Today's numbers for the two clocks of the question:

What the table says, in the owner's words:

1. **gc.** JVM launcher: 26 young collections per pass free 14.9 GB; 0.56 s of pauses in which all 8 workers
   stand still while the collector thread works (0.58 s of CPU): **2.6 % of the pass**. Native image: 121
   collections per pass free 20.9 GB; 2.18 s of pauses, **8.2 % of the pass** - and the image pays for memory a
   second time in the kernel: 7.7 s of kernel CPU for 6.3 million page faults per pass, 1.0 s of wall clock
   (the JVM: 0.44 s; it touches its 13 GB heap once and re-uses a 1 GB nursery). Memory management is 2.3 s of
   the 4.55 s between the two platforms (section 3.3); the rest is that C2's code for the workers needs 12 %
   less CPU than the image's.
2. **hash consing.** The largest item on both platforms: **27.6 % of the workers' CPU on the JVM (40.9 s CPU,
   5.1 s of the 21.9 s), 25.4 % in the image (44.5 s, 5.6 s of the 26.5 s)**. Four fifths of it are PROBES that
   end in a hit or in a miss (closures and tabling records 9.7 s, neutral applications 11.1 s, frames 6.2 s,
   constants and sorts 5.6 s on the JVM), 1.5 s hashing, 4.1 s writing the new records and runs, 2.8 s growing
   and re-hashing tables (89 % of that asked for by `Machine.addRecordAt`). It is NOT a cache-miss item as a
   whole: in the image its probes of closures, frames and neutral applications run at 4.2-4.4 instructions per
   cycle with average miss rates; the cache-miss items are table growth
   (IPC 2.1; 11 L1 misses per 1,000 instructions), the pair table, the **universe-level stores (IPC 1.8, half of
   their cycles stalled on memory, 12 % of all last-level misses for 3 % of the instructions)** and the kernel
   (section 3.2).
3. **num computation.** **0.1 % of the workers' CPU on the JVM (0.15 s CPU, 0.02 s of wall clock), 0.2 % in the
   image (0.39 s).** Nat folding is on the stack of 0.17 % of the samples. Mathlib does not compute: 273,045 Nat
   folds and 15,835 offset steps among 936.8 million judgment calls of a pass (statistics of the same jar).
4. **etc. - what is large and was not asked for by name:**
   - **Proof irrelevance is 0.12 % as code and 27.5 % as a context** (JVM: 40.8 s CPU, 5.1 s of wall clock with
     `Conv.pirr` on the host stack): the type inference, evaluation and comparison of types that the official
     proof-comparison rule triggers. The two shortcuts remove it: with them the workers need 105.3 s instead of
     148.3 s and the pass 15.71 s instead of 21.93 s (image: 20.40 instead of 27.20 s; section 4); what
     disappears is hash consing (-18.8 s), evaluation and code blocks (-12.4 s), memo lookups (-7.5 s).
   - **The reference-engine fallback for the 6,799 units (0.94 %) the machine declines (6,711 at eager
     reduction, 88 at other limits) is 12.5 % of the workers' CPU** (JVM 18.6 s, image 19.4 s; 2.3-2.4 s of wall
     clock), 58 % of it term-level substitution (`TermOps`, `Overlay`). The switch `eager` removes it: 18.07 s
     instead of 21.93 s (image: 24.18 instead of 27.20 s).
   - **Universe levels are 7.9 % (11.7 s CPU on the JVM, 10.9 s in the image)**: instantiating the level list of
     every constant that is evaluated and interning the result in the shared level store.
   - **Memo lookups that are not interning are 11.4 % (16.8 s)**, half of them the inline caches and block lookup
     of code blocks (7.8 s), then the pair table (4.7 s) and the tabling gate of EVAL (3.7 s).
   - **Reading the export's term nodes is 7.2 % (10.6 s)** on the JVM, where the readers' inlined frames are
     exact: application spines are walked node by node (`Terms.spineLength`, `spine`, `kind`).
   - **The load is not free in a pipelined pass**: loader thread, two scanner threads and the environment
     thread use 13.1 s of CPU on the same 8 cores (1.6 s of wall clock, 7.5 %).
   - Sessions (resets 0.14 %, slab growth 0.34 %), the driver (0.11 %), the worklist loop (0.02 %), admission on
     the worker (0.04 %), the JIT in a warm pass (0.1-1.2 %), deoptimisation (2 events per pass) and safepoints
     other than collections (none) are below 1 % each on the JVM.
5. **Against gruszka** (12.5 s wall, 75.6 s CPU with 8 threads on the same cores, `work/status/warm.md`): our
   164.1 s of CPU are 88.5 s more. With `eager` and the two shortcuts (section 4,
   configuration (c)) the JVM launcher's pass is **13.05 s and 100.7 s of CPU** (image: 17.16 s, 124.2 s): 0.6 s
   and 25 s away. So the
   difference is, in this order: the proof comparison (43 s of worker CPU), the fallback (17-21 s), and then 25 s

   lines that are not checking proper.

### 1.2 Times and shares come from different passes of the same process

A profiler distorts times. So:

- **Seconds** are from UNPROFILED passes: wall clock of the pass line (`rlvm: pass K/N ..`), CPU seconds per
  thread from `/proc/PID/task/TID/schedstat` (on-CPU and run-queue nanoseconds; `stat` for kernel time and
  faults), polled every 100 ms (cedar: 10 ms) by `work/prof/P10/tools/run.py` from a core outside the window's
  eight and interpolated at the pass boundaries; collections from `-Xlog:gc,safepoint` (JVM) and `-XX:+PrintGC`
  (image).
- **Shares** are from a LATER pass of the SAME process, to which the profiler is attached when the line of the
  last unprofiled pass has been read: `jcmd PID JFR.start` on the JVM (the process ran with
  `-XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints -XX:FlightRecorderOptions:stackdepth=1024` from its
  start: these change no generated code - on cedar the process with them is at 1.63-1.65 s in passes 5-6, the
  one without at 1.66-1.67 s in passes 7-8), `perf record -p PID` in the image.
- An item's CPU seconds = its share of the worker samples of the profiled pass x the workers' CPU seconds of
  the unprofiled pass. Its wall-clock seconds = CPU seconds / 8: the pass runs 8 workers on 8 cores, and level 1
  shows that the cores are busy for all but a few percent of the pass, so a CPU second anywhere costs an eighth
  of a second of wall clock.

### 1.3 The samples

- **JVM: `jdk.CPUTimeSample`** (JEP 509, JDK 25; `work/prof/P10/tools/p10.jfc`): a per-thread CPU-time timer of
  2 ms, so every thread is sampled in proportion to the CPU it uses (the classic `jdk.ExecutionSample` takes a
  few threads per wall-clock period; recorded too, as a cross-check). With `DebugNonSafepoints` a sample names
  the interrupted pc's whole inlining chain, and the stack below it. Host recursion of the machine reaches depth
  128 before a judgment is suspended to the machine's own stack, so the Java stack carries the judgments that are
  in progress (up to 1,024 frames are recorded; 8 of the 78,186 Mathlib stacks were cut at that depth).
- **Native image: `perf record`** inside the arena container (`bench/arena-docker.sh --arena-limits`), events of
  the X925 PMU (`armv8_pmuv3_1`) with fixed periods: `cpu-clock` 1 ms, `cpu_cycles` 8,000,009, `inst_retired`
  20,000,003, `l1d_cache_refill` 80,021, `l2d_cache_refill` 60,013, `ll_cache_miss_rd` 12,007, `br_mis_pred`
  80,021, `dtlb_walk` 2,503, `stall_backend_mem` 2,000,003 (about 4,700 samples per thread-second in all). No
  call chains (the image keeps no frame pointer); every sampled address is resolved into its chain of INLINED
  frames with the DWARF info of `dist-sym` (`gdb`'s block table; `tools/perf-items.py`).

### 1.4 One item per method: `work/prof/P10/items.map`

A text file of rules `KIND ITEM fully.qualified.Class#method` (first match wins), read by both classifiers
(`tools/JfrItems.java`, `tools/perf-items.py`):

- `item`: the INNERMOST frame of a sample that has an item names the sample's item ("what is being done").
  `Hash.record` inlined into `Values.closureProbe` inlined into `Eval.app` is hashing; the `Terms.kind` read
  inlined into `Infer.twalk` is a term-store read.
- `skip`: no item of its own - the sample goes to the next outer frame: JDK code, the one-line record readers
  (`Values.kind`, `Runs.arg` ..), the static forwarders of `Ops`.
- `ctx`: a context that wins over the innermost frame when it is anywhere on the stack: the reference-engine
  fallback (`rlvm.ref.*`, `Worker.reference`: "and everything it calls in the store"), and the decoding of a
  unit's proof block (`ProofBlocks.decode` and the overlay nodes it writes).
- Second column of every table, "by compile unit": the item of the OUTERMOST frame of the sampled frame's
  inlining chain, i.e. of the compiled method the pc is in - who asked. It is what a symbol-level profile sees,
  and the gap between the two columns is what inlining hides from one.
- `incl NAME`: markers for inclusive counts (samples with a judgment anywhere on the host stack), used for proof
  irrelevance, the K rule, structure eta.

To re-make the table after a change: run a window script, then `tools/post-jvm.sh` / `tools/post-native.sh`; the
classifiers print the methods that no rule names.

### 1.5 Error bars

- **Wall clock**: two later passes of one process differ by up to 6 % (21.93 and 23.27 s with the same CPU:
  the difference is core time that other processes of the loaded host took on the measurement cores - the
  process's threads were runnable and waiting meanwhile, level 1 shows it as its own line). Worker CPU of two
  later passes: within 1 %.
- **Sampling**: 78,186 worker samples (JVM, Mathlib) and 184,544 (image): a 10 % line has a standard error of
  0.1 point, a 1 % line of 0.04 point. Recorder losses: 0.3 % of the JVM samples; the samples x 2 ms cover 99.2 %
  of the workers' CPU of the profiled pass.
- **JVM, where the pc is**: 95.9 % of the Mathlib samples are taken at the interrupted pc, 4.1 % at the next
  safepoint ("biased"). The exact samples alone give every group within 0.4 point of the table; the classic
  sampler (`jdk.ExecutionSample`, 20,614 samples) within 0.8 point (fallback 13.3 against 12.5 %).
- **Inlined frames**: the innermost-frame column depends on the compiler's debug information for inlined
  one-line readers. On the JVM it is exact to the instruction (`DebugNonSafepoints`); in the image the readers of
  `Terms` are attributed to their callers more often (term-store reads 2.9 % against 7.2 %, with conversion
  and inference correspondingly higher: groups 3 + 6 + 7 together are 31.3 % on the JVM and 29.7 % in the
  image). Between neighbouring lines of that kind the two platforms differ by up to 4 points; the groups that
  have their own loops (hash consing, memo, evaluation, levels, fallback) agree within 2.5 points.
- **The profiled pass is slower** (JFR: +5.4 % worker CPU, +7.5 % wall on Mathlib; perf: +2.9 % and +2.8 %). The
  shares are of the profiled pass; the seconds are of the unprofiled one. If the recorder's overhead is not
  proportional (it is paid per sample, i.e. proportionally to CPU time), a line can be off by a fraction of that.
- **Image: no stacks.** A native sample has no caller. The reference fallback's use of the store (substitution,
  node reads) is split off with the caller split measured on the JVM for the same corpus and switch set (the
  fragment "Caller split" in section 3.2 lists the fractions): the image's fallback line is an estimate to that
  extent (its own code, `rlvm.ref`, is 3.1 % measured; 11.1 % with the split).

## 6. What surprised, and what could not be attributed

What surprised:

1. **"gc" is two different answers.** On the JVM launcher it is 2.6 % of the pass and not worth a line. In the
   image it is the second-largest line of level 1 after the workers: 2.2 s of pauses per pass (121 collections,
   one per 170 MB, where the launcher's 1 GB nursery makes 26, one per 570 MB), and the kernel time of 6.3
   million page faults on top (7.7 s of CPU). AR1's instruction view could not see either.
2. **Numeric computation is nothing** (0.1 %): the owner's third example is the smallest line of the table.
3. **Hash consing is big and cache-friendly.** A quarter of the workers' CPU, but at an IPC above 4 with average
   miss rates: the cost is the number of probes (instructions), not the memory. Making a probe cheaper buys
   little; making fewer of them is what the shortcuts do (-18.8 s of its 40.9 s).
4. **Universe levels are a top-five line** (7.9 %, and 11 % of what is left in configuration (c)) and the one
   real cache-miss item of the machine: every evaluated constant with level parameters instantiates its level
   list (`Levels.lsubList`, a 2^n-entry direct-mapped cache in front) and interns it in the shared store
   (`IntListStore.intern`, `LevelStore.intern`).
5. **Proof irrelevance costs nothing itself and a quarter of the pass through what it asks for.** No line of a
   flat profile shows it; the host stack does.
6. **0.94 % of the units are 12.5 % of the workers' CPU** (the fallback), and 58 % of that is the term store's
   substitution machinery, which the machine itself never calls.
7. **The measurement cores are not quiet**: between two passes of one process the wall clock moved by 1.3 s
   (6 %) with identical CPU; other processes took 4-10 % of the eight cores inside a window. Level 1 separates
   it; a single wall-clock number does not.
8. **The JVM has nothing left to give by itself**: 99.999 % compiled frames, 2 deoptimisations, no safepoint
   other than collections.
9. **The code blocks' inline cache for constants (`Code.kConst`) is 3.4 % by itself**: one probe of a table that
   is indexed by (site, level substitution); in the image 35 % of the cycles of the inline-cache and block-lookup
   line are stalled on memory.
10. **A `VarHandle` that is free on the JVM costs the image's scanner threads 17 % of their CPU** (`Mem.u64`,
    1.3 s per pass): the image does not turn the byte-array view handle into a load.
11. **The machine tries every declined unit twice** (13,598 declines for 6,799 units) before the reference
    engine gets it: with `eager` both the wasted attempts and the fallback go.

What could not be attributed, or only with a caveat:

- **Nothing is left over in the sample accounting** (JVM: every worker sample has an item; image: 0.04 % vdso,
  0.4 % array-copy stubs sampled without a caller, 3.7 % kernel as one line - the kernel's symbols are not
  readable in the container, so page faults, `madvise` and the clearing of new pages are not separated; the
  fault counts say it is mostly first-touch faults).
- **The collector's own CPU in the image** is inside the workers' and loader's lines and only partly visible
  (collector code 0.2 %, copies below 0.4 %); the rest of a pause is waiting for all threads to stop, and kernel
  work. The pause total is exact (`-XX:+PrintGC`); its split is not.
- **The fallback's store work in the image** is split off with the JVM's caller ratio (no stacks in the image).
- **What a judgment triggers after it was suspended to the machine's own stack** (5.6 % of the samples are such
  continuation steps): the inclusive lines of section 2.3 miss it; the ablation of section 4 does not.
- **Inlined one-line readers in the image**: `Terms` reads are partly counted under their callers there (section
  1.5). The JVM column is the one to read for the term store.
- **Declarations**: this report is by item, not by declaration (P8 and P9 have that view). For the numeric
  0.1 % the counts say only this much: two thirds of Mathlib's Nat folds (0.55 M of 0.82 M) are in the 6,711
  units that enter eager reduction, which the default configuration hands to the reference engine (section 4).
- **JFR against perf on one platform** was not possible (perf does not work on the host, JFR not in the image):
  the cross-check is across platforms, which mixes the compiler into it.

## 7. Files, and how to re-make the tables

Everything is under `work/prof/P10/`:

| what | where |
|---|---|

| distributions | `dist/` (`BUILD-INFO.txt`: jars, flags), `dist-sym/` (same jars + `-g`; `tools/build-sym.sh`) |
| window scripts (one `bench/quiet.py` window each) | `w/lib.sh` (run lines `jvm`, `jvmj1`, `native`, `nperf`), `w/one.sh`, `w/q.sh` (slot, window, log), `w/cedar1.sh` |
| runner: stamped output, per-thread CPU / run queue / kernel time / faults per pass, profiler hook after pass K | `tools/run.py` |
| JFR settings; classifier of JFR samples | `tools/p10.jfc`, `tools/JfrItems.java` (`tools/jfr-items.sh`) |
| perf in the container; aggregation; address -> inlined frames -> items | `tools/perf-run.sh`, `tools/perf-agg.py`, `tools/perf-items.py` |
| tables | `tools/table.py` (level 1, level 2, inclusive, contexts, hardware events), `tools/jit.py` (item 9), `tools/answer.py`, `tools/compare.py`, `tools/methods.py`, `tools/ar1check.py` |
| everything again from the raw files | `tools/regen.sh`; this document: `tools/mkdoc.py doc/P10.tmpl.md docs/research/profiles/P10.md` |
| raw files per run | `data/mathlib/`, `data/cedar/`: `<run>.out` (stamped output), `.threads.json`, `.gc.log`, `.jit.log`, `.jfr`, `.perf.json` + `.maps`, `.items.{json,txt}`, `.report.md`, `.frag/`, `.table.json` |
| window logs | `logs/w-*.log`; `work/perf-history/quiet.log` |

To re-make the table after a change of the machine:

```
scripts/build.sh --published --no-pgo --dist work/prof/P10/dist          # under bench/slot.sh -c ni -n 2
bench/slot.sh -c ni -n 2 -- work/prof/P10/tools/build-sym.sh             # the image for perf
O=$PWD/work/prof/P10/data/mathlib; X=$PWD/work/exports/mathlib.ndjson
work/prof/P10/w/q.sh m-jvm-ship-jfr 24 jvm $O/jvm-ship-jfr 100 "" 3 4 $X        # 3 unprofiled passes, JFR on pass 4
work/prof/P10/w/q.sh m-native-perf 24 nperf $O/native-perf 2 3 "" $X           # 2 unprofiled passes, perf on pass 3
work/prof/P10/w/q.sh m-native-plain 24 native $O/native-plain 100 "" 3 $X      # the shipped image on the host: times
work/prof/P10/tools/regen.sh                                              # tables in out/ and data/*/<run>.report.md
```

A method that no rule names shows up as `unassigned` (JVM) or `runtime` (image) in `<run>.items.txt` with its
share; a new class needs one line in `items.map`. Level 3 runs: the same lines with `-X machine.switches=..`
appended (`logs/` has the exact commands in the first line of every `.out`).
