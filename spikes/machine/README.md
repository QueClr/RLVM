# spikes/machine - machine-tier spike

Question: for the kernel's most frequent operation - instantiating a constant's type telescope with the
arguments of an application spine - **how much does elaboration into code objects buy, and is the hot path
worth compiling with Truffle?** Plus three side questions: the price of a first-order worklist machine
(experiment 2), of off-heap arena access (experiment 3), and whether heat concentrates differently in a larger
corpus (experiment 4).

All instruction counts are `perf stat -e instructions:u` over the whole process tree, taken with
`bench/arena-docker.sh --arena-limits bench/measure.sh` (8 performance cores, 16 GB), i.e. the arena's metric.
Host: aarch64 (Cortex-X925), GraalVM CE 25.5.5.0.3, Oracle GraalVM 25.0.4. Corpus: the arena's `init`
(347.8 MB, 6,137,092 expression records, 59,979 constants) and `std` (584.3 MB, 9,928,514 records,
103,885 constants) exports. Full tables: *agentic-note*: rep-spike-machine (generated by `scripts/tables.py` from
`results/*.txt`).

## 0. Results in one page

Workload (Init): 2,088,996 constant-headed maximal application spines, 8,350,959 arguments (4.0 per spine),
39,783 distinct head constants, 4.17 M distinct values produced. Per spine a code object executes 5.83
instructions (3.31 of them `MOV`) and 5.00 hash-consing probes; 25 % of the spines need no probe at all.

1. **Elaboration alone buys 1.4x-1.7x on Init and 2.1x-2.9x on Std** over a competently written generic
   evaluator with a closed-term memo (2.0x-2.5x on Init over one without). The first number of each pair
   charges the elaboration of every used constant (15.6 k instructions per constant, 0.62 G = 19 % of (b)'s
   net cost on Init) to the single pass; the second is the steady state (Init) or excludes elaboration (Std).
   85 % of the used constants are instantiated fewer than 10 times and never repay their elaboration, so it
   should start at a heat of 10-20 (section 4.3).
2. **Compiling code objects with Truffle does not pay at any threshold on Init or Std.** A compilation costs
   47-75 M instructions per root when the compiled code only calls the operation library ("call-threaded")
   and 220-530 M when the hash-consing probes are inlined. Compiled code then saves 158-199 (call-threaded)
   or 300-455 (inlined) instructions per instantiation in a native image. Break-even heat: **0.23-0.30 M
   instantiations (call-threaded), 0.7-0.9 M (inlined)**. The hottest constant, `Eq`, has 232,861 in Init and
   352,503 in Std. Measured totals on Init, native CE: (b) 6.38 G; promotion at heat 1e5 / 1e4 / 1e3 gives
   6.63 / 8.26 / 15.1 G call-threaded and 7.36 / 21.7 / 68.9 G with inlined probes. Extrapolated to
   mathlib (17.4x Init) fewer than ten constants cross break-even, for a gain of at most 2.5 G (0.6 % of the
   leader's 394.9 G) [estimate, section 4.5].
3. **What the Truffle tier really buys is a better compiler for the operation library, and most of that can
   be had without it.** One `mkApp` probe (hit) costs 110 instructions as written (static library, three
   small methods, arrays in static fields) in a CE native image, 96 with Oracle GraalVM, 38 under the JIT.
   The same probe expanded in place with the arrays in locals costs **45** (CE) / 50 (Oracle) / 33 (JIT).
   Rewriting only the stepper's APP path that way ((b2)) removes 21 % of (b) in CE; `-O3` removes 9 %,
   Oracle GraalVM 7 %, Oracle PGO 15 %.
4. **The cost is hash-consing, not dispatch.** Removing dispatch and operand decoding entirely (call-threaded
   compiled code) saves 15 %. Not building the domains at all (match mode) saves 21 % even though the result
   type is still built. The instruction set should be designed around avoiding probes.
5. **Wall clock is decided by the working set, not by instructions.** The same steady-state pass of (b) costs
   38 ns per spine with a 0.6 MB working set, 114 ns with 9 MB and about 330 ns with the whole of Init in one
   arena (116 MB), at identical instruction counts; (a1) and (b) differ by 1.7x in instructions but only
   1.2x-1.3x in wall time once the arena is DRAM-resident.
6. **Worklist machine vs host recursion (NbE of all 59,979 declaration types): 1.18x-1.32x** instructions for
   a machine whose control state is the program counter, 1.32x-1.58x for one with a mode register; the
   lower figure of each pair is with hash-consed values, the higher with bump allocation (nothing else to
   dilute the control cost).
7. **Arena access: keep `int[]`.** `sun.misc.Unsafe` changes nothing in a native image (1.01x);
   `MemorySegment` costs 1.35x-1.51x there. In JVM mode the differences are below the JIT's run-to-run
   noise.
8. **JVM mode depends entirely on the host JIT.** With the GraalVM JDK's defaults (Graal as host JIT,
   tiered) this 1-second workload costs 21 G more than a native image, with a run-to-run spread of 2-7 G;
   the steady state is 0.5x-0.9x of the CE native image per spine but could not be pinned down better than
   +-40 %. With `-XX:-UseJVMCICompiler -XX:-TieredCompilation` (C2 only, the configuration docs/research/10
   recommends) one pass costs 8.86 G for (b) against 6.38 G (CE image) and 5.17 G (Oracle image), repeats to
   1 %, and the steady state is 935 instructions per spine for (b), between the CE image (1167) and the Oracle
   PGO image (996). Two things are worse under C2: the hand-inlined stepper (b2: 1030) and the worklist
   machines (1.43x-1.56x of recursion for the program-counter machine, 2.45x-2.53x for the mode-register
   machine). Creating a Truffle engine costs about 2 G there and nothing measurable in a native image.
9. **Heat concentration does not change with corpus size** (Init -> Std): top-1 11.1 % -> 11.3 %, top-100
   71.7 % -> 66.8 %; constants with heat >= 1e3 / 1e4 / 1e5: 184 / 33 / 2 -> 255 / 50 / 3, i.e. counts above
   a fixed threshold grow like the corpus (1.5x).

## 2. Reproduce


Single runs (`. ./env.sh` first; `J=` JVM, `N=` native image):

```bash
J="$JAVA_HOME/bin/java -XX:+UseSerialGC -Xmx6g --enable-native-access=ALL-UNNAMED \
   --sun-misc-unsafe-memory-access=allow -cp $OUT/target/machine.jar:$OUT/target/lib/*"
S="-Drlvm.tbits=24 -Drlvm.hcap=14000000"       # arena pre-sized for Init: no growth in any variant
$J rlvm.spike.machine.Main parse $DATA/init.ndjson $OUT/init.bin        # once; parsing is never measured
$J rlvm.spike.machine.Main heat $OUT/init.bin                            # heat distribution
$J $S rlvm.spike.machine.Main verify $OUT/init.bin                       # a0, a1, b, b2: identical ids?
$J $S -Drlvm.threshold=1000 rlvm.spike.machine.truffle.MainT verify $OUT/init.bin   # + three (c) set-ups
$J $S rlvm.spike.machine.Main profile $OUT/init.bin                      # instruction mix per spine
$J $S rlvm.spike.machine.Main exp1 $OUT/init.bin b                       # variants: none null a0 a1 elab b b2 brec bm
$J $S -Drlvm.threshold=10000 -Drlvm.inline=2 rlvm.spike.machine.truffle.MainT \
      --engine.TraceCompilation=true exp1 $OUT/init.bin c                # (c); see MainT.java for the knobs
N=$OUT/ni/machine-ce
$N $S -Drlvm.threshold=10000 -Drlvm.inline=0 exp1 $OUT/init.bin c
$OUT/ni/machine-ce-fin -Drlvm.intern=false exp2 $OUT/init.bin wl2       # experiment 2: rec | wl | wl2
# one measured run, exactly like the batches:
$RLVM_ROOT/bench/arena-docker.sh --arena-limits --no-network $RLVM_ROOT/bench/measure.sh -- $N $S exp1 $OUT/init.bin b
```

Measurement protocol. A run loads the binary cache, derives per-node facts, extracts the spines (this is
`none`), then executes one variant. Costs are differences between whole-process counts of the same binary:
`null` (driver loop with an empty instantiator) - `none` = driver; variant - `null` = variant; a 3-pass run
minus a 1-pass run, halved, = one steady-state pass (every value already interned). Native-image counts repeat
to 4 digits (spread <= 0.02 G except where Truffle compiles in the background); JVM counts spread by 2-7 G, so
JVM steady state uses 21/41/81-pass runs and is still only good to +-40 % with the default (Graal) host JIT.
The main batches have 2 (native) or 3 (JVM) repetitions and tables show medians; steady-state rows are single
pairs of processes unless several estimates are listed.

Builds. Two builds of the same sources were measured: "frozen" (jar `frozen/`, images `machine-ce`,
`machine-ee`, `machine-ce-m0..m3`, `machine-ee-m0`, `-O3`, `-pgo`: batches exp1-*, hot-*, exp3, exp4-*) and
"final" (jar `frozen2/`, images `machine-ce-fin`, `machine-ee-fin`: batches exp2, final-images, micro,
steady-jvm, long-jvm). "final" adds `Stepper2`, `Micro`, the `APPEQ` pattern and the inlined `EQ` test of
match mode, `Exp2.normalizeWl2` and launcher commands. The class files of `Vals`, `Mem`, `Generic`,
`Workload`, `Corpus`, `Instantiator$StepperInst`, `Instantiator$GenericInst`, `TelRoot`, `TOps`, `TruffleInst`
are byte-identical in both (checked with `cmp`), and variant (b) costs 6.377 G in `machine-ce`, 6.374 G in
`machine-ce-m0` and 6.368 G in `machine-ce-fin`. `scripts/build-all.sh` builds everything from the final
sources, so a reproduction has one build under two names.

## 3. What is executed

### 3.1 Workload

A spine root is an `app` record referenced from at least one non-function position (argument, binder type or
body, let part, projection target, declaration type/value, recursor rule). For every such record whose head is
a constant `c` with arguments `a1..ak`, in file order, the operation is: with `T_c = Pi x1:A1 ... xn:An. R`
and `j = min(k, n)`, produce `A_i[a1..a_{i-1}]` for `i <= j` and the result type (`R[a1..an]` if `k >= n`, else
the closure of the remaining Pi telescope). Arguments are opaque atoms, universe levels are ignored, constants
are opaque, so the only reductions are beta and zeta inside the type. Over-applied spines (1.5 %) stop at `n`.

|---|---|---|
| expression records / `app` records | 6,137,092 / 5,228,615 | 9,928,514 / 8,090,565 |
| constants / used as a spine head | 59,979 / 39,783 (66 %) | 103,885 / 69,712 (67 %) |
| spines with a constant head / other head | 2,088,996 / 43,460 | 3,115,533 / 71,309 |
| arguments (per spine) | 8,350,959 (4.00) | 12,832,493 (4.12) |
| under-applied / over-applied | 88,268 / 30,482 | 132,493 / 47,489 |

| per spine in (b): instructions / code words / probes / spines with no probe | 5.83 / 17.7 / 5.00 / 25.2 % | 6.01 / 19.0 / 5.70 / 24.0 % |
| instruction mix per spine (MOV, APP1, APP2, APP3, APPN, APPD, CLO) | 3.31, 0.50, 0.70, 0.63, 0.13, 0.20, 0.36 | 3.20, 0.57, 0.72, 0.63, 0.22, 0.21, 0.46 |

### 3.2 Values (`Vals.java`)

A value id is an `int`: negative = opaque atom `-(x+1)` (never stored); positive = word offset of its record
in the arena. Word 0 is the header (kind in bits 0-3, auxiliary number in bits 4-31):

```
APP    [hdr, fn, arg]                       neutral spine cell (binary, so prefixes are shared)
PROJ   [hdr | idx<<4, struct]     SORT [hdr, level]     CONST [hdr, name]     LIT [hdr, expr]
LAM/PI [hdr | ncap<<4, expr, cap_1 .. cap_ncap]         closure trimmed to its free variables (fvMask order)
```

Hash-consing: open addressing, linear probing, power-of-two `int[]` of value ids, keys compared against the
arena words. Measured: 5.0 probes per spine, 0.1 collision steps per probe at load <= 0.25. Every constructor
is `findK` (probe only: no allocation, no exception) + `insK` (slow path), so that Truffle partial evaluation
can inline the first and stop at the second. No memo slots (the real layout of doc 09 has 4 more words per
value; that changes cache footprint, not instruction counts).

### 3.3 Code objects (`Elab.java`)

One per constant, elaborated lazily at its first instantiation. Frame (relative to `fp`): slots `0..n-1`
arguments (pushed by the caller: the machine's value stack is the frame), `n..2n-1` domain outputs, `2n`
result, `2n+1..` temporaries. Operand: `> 0` immediate value id (pre-interned closed sub-term, including
closed spine prefixes such as `@Eq Nat`), `<= 0` slot. Straight-line blocks: one per domain, one result block
per arity `0..n`.

```
MOV  dst src                  APP1/APP2/APP3 dst f a [b [c]]        APPN dst cnt f a1..acnt
APPD dst cnt f a1..acnt       head may be a closure at run time (parameter in head position, let-bound
                              lambda, beta redex): checks, and falls back to the generic evaluator
PROJ dst hdr s                CLO dst hdr e c1..cn    (captures = operands, ascending de Bruijn order)
```

Example (hand-written from the layout): `Eq.trans : {α : Sort u} {a b c : α} (h1 : a = b) (h2 : b = c) : a = c`
has n = 6 and becomes `MOV s6 <- #Sort_u; MOV s7 <- s0; MOV s8 <- s0; MOV s9 <- s0; APP3 s10 <- #Eq s0 s1 s2;
APP3 s11 <- #Eq s0 s2 s3` and the result block `APP3 s12 <- #Eq s0 s1 s3` (plus six `CLO` blocks for partial
applications). `Eq` itself is four `MOV`s.

Elaboration statistics on Init: 39,783 code objects, 2.82 M code words (71 per constant), 546,749 instructions
(MOV 139,118, APP1-3 210,550, APPN 29,893, APPD 8,453, PROJ 245, CLO 158,490), 392,447 immediate and 985,190
slot operands, 20,298 CSE hits. The CLO count is inflated by the eager result block per arity.

Match mode (`brec`/`bm`): every domain is also elaborated into a pattern (`EQ op`, `APPEQ cnt ops head`,
`APP cnt P.. P_head`, `PROJ`, `CLO`, `BUILD` = fall back to code + id comparison) that `Stepper.match` walks
over an existing value without hashing. On Init: 146,535 EQ, 71,191 APPEQ, 34,902 APP, 22,439 CLO and 1,363
BUILD patterns. The "existing value" stands for the argument's type; in the spike it is the domain value a
previous build pass produced, so every match succeeds (0 failures in 8.3 M matches).

### 3.4 The three variants and their verification

- (a) `Generic.eval`: walks term nodes with an array environment, peels spines iteratively, trims closures by
  `fvMask`; `a1` adds a memo for closed terms (per expression id), `a0` has none.
- (b) `Stepper.exec`: `while (pc < end) switch (code[pc] & 0xff)` over the code object; (b2) `Stepper2.run`:
  the same in one method with table/arena in locals and the APP probe expanded in place.
- (c) `TruffleInst`: the stepper is the base tier. A per-constant counter is incremented on every stepped
  instantiation; at the threshold the code object becomes a `TelRoot` (one node per instruction, operands as
  PE constants, temporaries in static frame slots, one straight-line sequence per arity seen so far) and is
  submitted with `OptimizedCallTarget.compile(true)`; instantiation keeps stepping until `isValid()`, then
  enters compiled code with `call(..)`. The Truffle interpreter is never executed. An arity that was not
  profiled returns to the stepper without deoptimisation. `-Drlvm.inline=0` makes every operation a
  `@TruffleBoundary` call into the same AOT library ("call-threaded"), `1` inlines the APP/PROJ probes, `2`
  also the closure probes.

Verification (`results/verify.txt`): all variants run one after the other in ONE arena; because values are
hash-consed each must return exactly the ids of the reference run for all 10,398,595 outputs. Result:
`a0 = a1 = b = b2 = c(inline 2) = c(inline 0) = c(inline 1, callIndirect)`, IDENTICAL ids. (b) interns 34,133
additional values, the closed sub-terms of telescope parts that no spine reaches. Separately, (b) and (b2) run
alone from a 4,096-slot table give the same checksum, which exercises insertion and growth.

### 4.3 Elaboration

0.622 G for 39,783 constants in CE = 15.6 k instructions per constant (Oracle 16.9 k; Std 21.9 k; JVM one-pass
122 k, i.e. interpreted and C1 code). It saves 863 instructions per instantiation in steady state
((a1) - (b)), so a constant repays it after about 18 instantiations. 33,781 of the 39,783 used constants have
heat < 10 and receive 3.3 % of the instantiations (70 k spines): elaborating them costs about 0.53 G and
returns 70 k x 863 = 0.06 G. With those constants left to the generic evaluator, (b)'s net cost on Init would
drop from 3.20 G to about 2.73 G [estimate: 3.199 - 0.53 + 0.06] and (a1)/(b) rise from 1.38 to 1.6. Elaborating result blocks per arity on demand removes most of the 158,490 CLO instructions emitted
(only 0.36 CLO per spine execute).

### 4.4 Calibration: where the instructions go

| instructions per operation | JVM (Graal JIT) | native CE | native Oracle |
|---|---|---|---|
| empty loop iteration | 9.6 | 11.0 | 11.0 |
| `Vals.mkApp`, value exists (hit) | 38 | 110 | 96 |
| the same probe expanded in place, table/arena/mask in locals | 33 | 45 | 50 |
| `Vals.mkApp`, new value (insert) | n/a | 156 | 125 |
| closure with 2 captures (hit) | 48 | 192 | 187 |

In the CE image `Vals.find3` alone is 70 instructions on the hit path (disassembled): a stack-overflow check
and a safepoint poll per call, three static-field loads with compressed-reference decoding and null checks,
constants materialised with `mov/movk`, bounds checks. `mkApp -> find3` is not inlined by the AOT compiler.
Hence, per spine in CE: 4.64 APP probes x 110-156 + 0.36 closures x 190 = 580-790 of (b)'s 1167-1234; the
rest is dispatch, operand decoding and the two block calls.

Observations.
- The number of compilations is what costs: a compiled root is on average 2.1 kB of machine code and 16 ms
  of compiler time call-threaded, 7.3 kB and 66 ms with inlined probes (JVM mode,
  `--engine.TraceCompilation`, the 33 hottest roots); one compilation equals 40,000-400,000 stepped
  instantiations.
  Compilation runs on other threads, so wall time rises little (1.07 s -> 1.65 s at heat 1e3 inlined) while
  the instruction count rises 10x. The instruction count is the board metric.
- With background compilation the code arrives late: at heat 1e3 only 50-67 % of the spines run compiled
  although 68.7 % happen after the threshold.
- Requesting first-tier compilation is not an option: first-tier code is slower than the stepper and
  triggers a last-tier compilation on its own after 10,000 calls (hot rows `tier1` in *agentic-note*: rep-spike-machine).
- Against the better base tier (b2) the saving of inlined compiled code shrinks to about 210 instructions
  per spine and call-threaded code saves nothing [estimate: (b2)/(b) = 0.79 applied to the hot subset].
- Mathlib estimate. 107.04 M expression records x 0.34 spines per record = about 36 M spines; if shares stay
  as in Init/Std, the constants above the inlined break-even (0.78 M = 2.2 % of 36 M) are the 7 hottest;
  their instantiations beyond break-even are about 6.0 M, x 418 = 2.5 G. With (b2) as the base: `Eq` and
  `Eq.trans` only, about 0.5 G.

## 5. Experiment 2: worklist overhead

`Exp2.java`: eval + readback of every declaration type of Init (59,979 types), constants opaque, closures over
hash-consed linked environments, normal forms hash-consed. `rec` = recursive Java; `wl` = one loop, explicit
continuation stack in an `int[]`, control state in a mode register (EVAL / RETURN-VALUE / READBACK /

transition that stays in its phase is a jump). All three call the same library in the same order: identical

## 8. Caveats

- **Simplified operation.** Arguments are opaque atoms and levels are ignored. With real values the 0.20
  `APPD` per spine (a parameter in head position, e.g. `motive t`) do real beta reductions; with real
  universe polymorphism a sub-term mentioning a level parameter is not closed, so fewer operands are
  immediates (here 4.27 of 10.84 per spine) and `Sort u`-style domains need a level operation.
- **Static heat.** Each distinct spine is instantiated once; real checking re-infers per declaration and
  instantiates in whnf/def_eq. Break-even heats are per instantiation and unaffected; which constants reach
  them is not.
- **Only telescope instantiation was promoted to Truffle**: straight-line code dominated by library calls,
  the least favourable case for a JIT. Nothing here says what compilation buys for code objects with loops
  (recursor iteration on closed terms, where spikes/platform measured 45x).
- **The Truffle variant uses two non-public methods** (`OptimizedCallTarget.compile`, `isValid`), needs
  `--add-exports org.graalvm.truffle.runtime/com.oracle.truffle.runtime=ALL-UNNAMED` for native-image, and
  has no deoptimisation path. An early version whose root used `break` inside `@ExplodeLoop` produced
  quadratic code (18 kB and 240 ms per root); the measured version dispatches on the arity first.
- **JVM numbers** are whole-process counts including JIT threads. One-pass totals are warm-up; steady-state
  estimates from pairs of processes disagree by up to 40 % (different JIT outcomes per process).
- **One arena for the whole corpus**, pre-sized (2^24 table slots, 14 M words) so that no variant grows:
  growth and session reset are not measured, and pass wall times are DRAM-bound (4.6).
- **Match mode** matches against values that are known to match; a mismatch path (build + def_eq) is not
  exercised. It was not ported to the Truffle tier.
- **aarch64**, not the arena's x86-64: bench/README measured 0.944 aarch64/x86-64 for the C++ kernel; the
  factor for native-image and JIT code is unknown.
- **Not measured**: (b2)-style rewriting of the generic evaluator and of closure probes; parallel workers;
  Oracle GraalVM in JVM mode; the two worklist machines under Truffle.
- **Against docs/research/10 and 11** (both appeared while this spike ran). Doc 10 finding 5 (a Truffle
  compilation is a net loss below about 100,000 calls) and finding 3 (CE native-image code executes 19-60 %
  more instructions than JIT code) agree with sections 4.5 and 4.4/4.7; here the gap for the library as
  written is larger (110 vs 38 per probe) and almost closes when the probe is expanded in place (45 vs 33).
  Doc 10 finding 10 reports `MemorySegment` 20-250x slower in a CE native image; with `static final` segments
  in a run-time-initialised holder class (`Mem.SegHolder`) and `ValueLayout.JAVA_INT` this spike sees 1.35x-1.51x
  on the whole variant. Doc 11 decision 4 (1.9x on the JVM) could not be confirmed or refuted here (section
  6). The default-JIT JVM numbers of this spike were taken before doc 10 recommended C2; section 4.7 adds
  that configuration.

## 9. Requirements on wave-2a modules

- `rlvm-export`: per expression node `loose` (max loose index + 1) and the 64-bit free-variable mask of doc 09
  section 1.2 (both the elaborator and the generic evaluator read them at every closure); per constant the
  telescope length and the type's expression id; static spine-head heat per constant (cheap in the same pass
  that marks non-function references: `Workload.build`). A flag "sub-term is closed and level-closed" would
  let the elaborator pre-intern without re-deriving it.
- `rlvm-level`: an id for an instantiated level list that can serve as an operand (code objects need
  `(constant, level arguments)` to key pre-interned immediates).
- Arena library: constructors split into probe (`findK`: no allocation, no exception, no call) and insert
  (`insK`), with the table array, arena array and mask obtainable as locals; that split is what both the
  hand-inlined stepper (b2) and Truffle partial evaluation need.
